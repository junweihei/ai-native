# AI Native 系统学习与统一成长树实践路线 V3.0

> 本文件是个人 AI Native 系统学习、真实产品实践和能力验证的权威战略总纲。
>
> V3.0 不以“在固定时间内学完一组知识”为目标，而以形成可解释、可判断、可实践、可验证、可迁移的企业级 AI Native 解决方案能力为目标。
>
> 整个学习过程以 AI Native 能力成长为主线，以“统一成长树”作为贯穿式真实产品实践载体，以可复查证据作为阶段升级依据。
>
> 时间用于管理投入，不用于替代能力判断；产品用于承载实践，不用于替代个人学习；AI 用于提高学习和工程效率，不用于替代最终判断与能力证明。

---

# 一、权威声明与使用方式

## 1. 文档定位

《AI Native 系统学习与统一成长树实践路线 V3.0》是当前 AI Native 学习项目的权威战略总纲。

它负责定义：

- 最终目标角色与能力状态；
- AI Native 能力结构；
- 学习系统总体架构；
- 七个能力阶段及依赖关系；
- 统一成长树实践主项目的定位；
- 能力等级、证据和阶段门禁；
- 时间投入、复杂度控制和停止规则；
- 学习者、GPT 与 Codex 的协作边界；
- V2.0 迁移与版本治理规则。

本总纲不提前制定长期固定的每日任务，也不替代当前阶段的详细执行计划。

核心原则是：

> **总纲规定方向、能力结构、运行规则和升级标准；阶段计划负责把这些规则转化为当前可执行任务。**

## 2. 内容源规则

正式采用：

```text
Markdown = 唯一权威编辑源
Git = 版本、差异、审查与跨设备同步机制
Word / PDF = 阅读、打印、汇报或阶段发布版本
学习界面 / 知识网站 = 可选辅助载体，不作为学习系统成立的前提
```

规则：

1. 战略总纲、阶段计划和核心学习成果优先在 Markdown 中维护。
2. 发生重要调整时，记录调整原因、证据和版本变化。
3. Word、PDF 等由正式 Markdown 派生，不形成独立权威版本。
4. Learning OS 的“运行模型”仍可作为上位原则；具体网站或界面不是前置条件。
5. 工具建设只有在已经出现真实效率问题、且收益明确时才进入实施。

如果辅助工具开始明显挤占 AI Native 学习，而其收益尚未被证明，应退回 Markdown、Git 和最小执行体系。

## 3. 文档权威层级

```text
第1层：学习运行原则与长期共识
└── 定义学习方法和长期不轻易改变的约束

第2层：V3.0 战略总纲
└── 定义目标、能力结构、阶段路线、实践主项目和门禁规则

第3层：当前能力阶段执行计划
└── 定义当前阶段的问题、资源、练习、实践、成果和验收

第4层：周 / 日任务与工程任务
├── 当日学习任务
├── 专项练习
├── 统一成长树产品增量
└── Codex TASK

第5层：成果、证据与复盘
├── 闭卷记录
├── 知识地图与案例
├── SRS / 架构 / 产品成果
├── 代码、测试、Eval、Trace
└── 阶段复盘与迁移结果
```

发生冲突时：

- 长期学习原则以上位运行共识为准；
- 能力方向、阶段依赖和升级条件以 V3.0 为准；
- 当前资源、任务和时间安排以当前阶段执行计划为准；
- 实际能力状态以成果和证据为准；
- 页面状态、任务勾选、文件数量和 AI 的判断都不能替代能力证据。

## 4. 使用方式

阶段开始前只回答：

1. 当前处于哪个能力阶段？
2. 上一阶段正式门禁是否通过？
3. 当前阶段的唯一核心问题是什么？
4. 统一成长树承担什么真实实践？
5. 本阶段必须留下什么证据？
6. 当前最大弱点是什么？

每周只确定一个主要问题或一个主要能力弱点，并明确其服务的阶段门禁、成果和验证方法。

每天主要使用当前阶段计划和当天任务，不要求重复阅读总纲；只有出现方向、架构、复杂度升级或阶段切换问题时才回到 V3.0 校验。

阶段结束时，根据闭卷、判断、实践、Eval、迁移等证据进行门禁检查。未通过时不增加大量新资料，只补当前唯一主要弱点。

## 5. 总纲更新原则

以下情况通常不修改 V3.0：

- 新增课程、文章或论文；
- 某周延期；
- 修改 Prompt 或 Tool；
- 一次工程失败；
- 某个阶段比预计多投入数小时；
- 产品局部功能调整。

只有最终目标角色、能力结构、阶段依赖、实践主项目适用性或学习运行模式被真实证据系统性否定时，才升级战略总纲。

# 二、目标角色与最终能力状态

## 1. 目标角色

V3.0 的最终目标是：

> **企业级 AI Native 解决方案架构者：能够把真实业务问题转化为受控、可验证、可集成、可治理并能够持续演进的 AI Native 系统。**

这一目标不是培养：

- 大模型算法研究员；
- 基础模型训练专家；
- 单一 Agent 框架专家；
- Prompt 技巧专家；
- 某一家模型或平台的产品专家；
- 只会调用现成 SDK 的应用开发者。

核心能力是：

> **从业务问题出发，理解 AI 的能力和边界，选择合理机制，并把业务、模型、Context、Workflow、Agent、Tool、企业系统、Eval、安全和治理组织成一致方案。**

## 2. 最终能力状态

完成 V3.0 后，应能够：

1. 从业务结果出发判断应使用规则、传统程序、单次模型、Context、Workflow、Agent、Tool 或混合架构。
2. 解释业务、交互、任务协调、Context、知识、模型、工具、企业系统、运行基础设施、评测和治理之间的关系。
3. 把概率性模型能力转化为具有 Input、Instruction、Structured Output、Schema、Validation、Failure Handling 和 Eval 的软件能力。
4. 设计数据来源、检索、Context Assembly、Citation、State、Memory、权限和生命周期。
5. 区分规则、Workflow、Agent 和 Multi-Agent，并设计 Tool Contract、Stop、Retry、Timeout、Budget 和 Human Approval。
6. 建立 Baseline、Eval、Failure Classification、Trace 和版本回归，用证据判断改进是否有效。
7. 把身份、委托、数据范围、工具权限、审批、审计、提示注入防护、幂等、回滚和人工接管纳入设计。
8. 借助 GPT、Codex 等 AI 工具完成原型与工程实现，同时能够读懂关键代码、日志、测试和失败结果。
9. 把一个真实 AI Native 问题从业务目标做到可验证结果，并将同一方法迁移到新的企业场景。

## 3. 最终核心交付物

V3.0 最终至少形成：

1. 一套持续演进的个人 AI Native 总知识地图；
2. 《统一成长树 AI Native 产品需求规格说明书 V1.0》；
3. 一个可运行、可演示、可验证的统一成长树 AI Native 产品 V1.0；
4. 一套版本化 Eval、失败分类和关键改进记录；
5. Context、Workflow、Agent、Tool、权限与治理相关设计成果；
6. 一个企业陌生场景迁移案例；
7. 《个人企业级 AI Native 解决方案方法论 V0.1》。

这些成果用于证明能力，不为了增加文档数量。

## 4. 不作为 V3.0 主线

- 大模型预训练、底层算法研究和大规模参数训练；
- 为追热点学习全部模型、框架和云产品；
- 没有真实任务的 Prompt 技巧收集；
- 没有 Eval 的 Demo 堆积；
- 为了学习 Agent、MCP、Multi-Agent 而人为增加复杂度；
- 为练代码而建设与学习目标无关的软件系统；
- 为展示成果而建设复杂知识网站；
- 在证据不足时提前锁死未来全部任务和技术方案。

底层原理、数学基础、框架源码和模型训练细节按当前理解缺口补充，不单独扩展为长期主线。

# 三、V3.0 学习系统总体架构

## 1. 三条主线

V3.0 同时运行三条互相约束的主线：

```text
知识与能力主线
    +
统一成长树实践主线
    +
个人能力证据主线
```

### 知识与能力主线

解决：

> 我是否真正理解 AI Native，并形成可用于真实问题的判断能力？

### 统一成长树实践主线

解决：

> 我能否把学到的能力转化成真实 AI Native 产品设计与工程结果？

### 个人能力证据主线

解决：

> 我是真的会了，还是只是看懂了课程、GPT 或 Codex 的答案？

三条主线最终汇合到：

```text
图 → 拆 → 练 → 用 → 证 → 迭代
```

并通过阶段门禁决定是否升级。

## 2. 学习与实践的基本关系

知识学习、统一成长树实践和个人能力证据必须形成闭环；具体运行步骤统一见第六章“统一学习运行闭环”。本章只定义三条主线及其七阶段总体架构。

## 3. 七个能力阶段

```text
S1 整体认知与机制判断
↓
S2 AI Native 需求深度学习工程
↓
S3 模型应用、结构化输出与 Eval
↓
S4 Context、检索与可信知识
↓
S5 Workflow、Agent 与受控 Tool
↓
S6 企业集成、MCP、治理与可观测
↓
S7 端到端产品化、企业迁移与个人方法论
```

阶段表示主要能力依赖，而不是禁止提前接触下一阶段概念。可以提前达到 L1 认知，但系统学习、专项实践和正式取证应服从阶段顺序。

# 四、能力等级与完成标准

## 1. 五级能力状态

| 等级 | 状态 | 判断标准 | 典型证据 |
|---|---|---|---|
| L0 | 未进入 | 尚未系统学习，或只知道名称 | 无正式证据 |
| L1 | 能解释 | 能用自己的话说明定义、作用、位置、关系和基本原理 | 闭卷总结、知识地图、口头讲解 |
| L2 | 能判断 | 能说明适用、不适用、主要权衡、失败条件和复杂度选择 | 案例判断、反例、方案选择、迁移题 |
| L3 | 能实践 | 能在练习或真实项目中正确使用，并处理常见失败 | SRS、设计、代码、测试、项目增量 |
| L4 | 能验证与改进 | 能建立评测标准，定位失败并基于证据持续优化 | Eval、Trace、指标、版本对比、复盘 |

## 2. 目标深度

- 核心能力：目标 L3～L4；
- 重要支撑能力：目标 L2～L3；
- 扩展认知：目标 L1～L2。

不是所有知识点都需要达到 L4。深度由最终目标、当前阶段和真实实践需要决定。

## 3. 核心节点完成条件

一个核心知识或工程节点至少需要：

```text
能够解释
+ 能说明它在整体系统中的位置
+ 能判断何时使用
+ 能判断何时不使用
+ 一个适用案例
+ 一个反例或失效条件
+ 一次练习或真实实践
+ 一项可复查证据
```

进入 L4 时再增加：

```text
Baseline
+ 失败样例
+ Eval / Trace
+ 至少一次基于证据的改进
```

产品成果不能自动证明个人能力达到对应等级；具体证据判定统一见第十八章“评测、证据与阶段门禁”。

# 五、六条长期能力主线

七个阶段解决“当前重点学什么”，六条能力主线解决“最终必须形成哪些横向能力”。

| 能力主线 | 必须掌握 | 最终能力证明 | 统一成长树主要验证位置 |
|---|---|---|---|
| 业务与产品 | 场景价值、用户结果、任务边界、AI适用性、风险与价值假设 | 用例、任务说明、SRS、价值与风险判断 | 成长目标、家庭任务、用户旅程、人机职责 |
| 模型应用 | Instruction、Prompt、Structured Output、Schema、模型选择、错误处理、成本与延迟 | 模型功能、样例集、失败分类、版本对比 | 观察理解、结构化判断、建议生成 |
| Context 与知识 | 数据来源、检索、组装、引用、权限过滤、State、Memory、生命周期 | Context Map、检索评测、引用与权限证据 | 儿童状态、家庭情况、成长历史、阶段目标、反馈 |
| Workflow / Agent / Tool | 模式选择、任务状态、路由、工具契约、重试、停止、恢复、人工确认 | 可追踪、可停止、可恢复的执行链 | 月度方案、周任务、反馈、复盘与工具调用 |
| 工程与评测 | 数据集、Baseline、Eval、Tracing、测试、回归、版本和成本 | Eval 集、失败分类、Trace、版本对比 | 推荐质量、任务可执行性、反馈效果 |
| 企业治理与安全 | 身份委托、最小权限、审批、审计、数据边界、注入防护、人工接管 | 权限矩阵、威胁模型、审计与安全证据 | 家庭/儿童数据边界、敏感操作、Tool 权限 |

治理与评测不是最后增加的附加能力，而是随系统复杂度同步增强。

# 六、统一学习运行闭环

所有重要知识节点、能力阶段和主要实践任务统一采用：

```text
图 → 拆 → 练 → 用 → 证 → 迭代
```

## 1. 图：建立结构和位置

至少回答：

- 它解决什么问题？
- 核心概念是什么？
- 位于整体 AI Native 系统哪里？
- 与上下游能力怎样连接？
- 怎样判断做得好？
- 什么时候不应该使用？

产出可以是知识地图、架构图、决策树、控制流或学习卡。

## 2. 拆：理解优秀成果为什么成立

默认采用：

```text
3 个优秀案例 + 1 个普通 / 失败 / 过度设计案例
```

重点识别：

- 关键决策；
- 成功条件；
- 证据；
- 反例；
- 失效条件；
- 可迁移规律。

案例学习只有在改变自己的判断模型时才真正产生价值。

## 3. 练：只解决一个主要弱点

```text
首次独立完成
→ 获得具体反馈
→ 找出唯一主要弱点
→ 只修改一个主要问题
→ 再做一次
→ 比较前后变化
```

练习应尽量小、明确、可比较、可验证、时间受控。

## 4. 用：进入统一成长树或真实任务

优先判断统一成长树是否存在真实问题可以承载当前能力。

有真实问题则进入需求、SRS、设计、代码或 Eval；没有则用最小练习完成验证。

不得为了让所有知识都“用上”而污染产品设计。

## 5. 证：离开资料证明能力

根据能力类型选择：

- 闭卷地图和口头讲解；
- 新场景选型与反例；
- 独立需求、设计或工程实现；
- Eval、Trace、Baseline、版本对比；
- 陌生领域迁移。

## 6. 迭代：证据决定下一步

只回答：

```text
哪里不好？
→ 证据是什么？
→ 为什么？
→ 当前最大问题是什么？
→ 下一次只改什么？
→ 通过标准是什么？
```

不通过增加大量资料或同时修改多个变量掩盖真实问题。

# 七、统一成长树 AI Native 实践主项目

## 1. 项目定位

统一成长树是贯穿 V3.0 的真实 AI Native 实践主项目。

它不是：

- 学习网站；
- 技术 Demo 集；
- AI Native 学习结束后的毕业作品；
- 为了使用某项技术而设计的实验产品。

它承担的职责是：

> **为学习提供持续、真实、复杂度逐步提升的问题环境，使知识理解、产品设计、工程实践和能力验证在同一个长期场景中形成闭环。**

## 2. 为什么适合作为主实践项目

它具备：

- 明确但不简单的用户结果；
- 持续变化的个体 Context；
- 规则、判断和生成混合问题；
- 连续运行与反馈循环；
- 可逐步形成真实 Eval；
- 能自然承载模型、Context、Workflow、Agent、Tool 和治理能力。

但所有技术使用都必须服从真实业务问题。

## 3. 项目原则

1. 产品首先解决真实用户问题，不为技术服务。
2. 学习阶段决定当前实践深度，不提前引入尚未掌握的复杂能力。
3. 每次只形成一个可验证增量。
4. 产品完成度不能替代个人能力证据。
5. 如果工程工作明显超过学习收益，允许降级为最小原型、设计或纸面推演。
6. 统一成长树负责长期深度实践，企业场景负责最终迁移和企业级约束验证。

## 4. 演进路径

```text
S1  问题与机制分析
↓
S2  业务模型 + SRS 需求基线
↓
```

# 八、AI Native 需求深度学习工程与 SRS 演进机制

## 1. 阶段意义

AI Native 需求设计除了传统软件的用户、场景、流程、规则和验收，还必须回答：

- 哪些问题适合 AI，哪些不适合？
- AI 具体负责什么？
- 需要什么 Context？
- AI 失败后业务怎样继续？
- 哪些步骤需要人工确认？
- 怎样证明 AI 改善了结果？
- 是否需要 Workflow、Agent 或 Tool？

因此，需求规格说明书（SRS）不仅是开发输入，也是：

> **业务理解、机制判断、架构思考和验证设计的深度学习载体。**

## 2. SRS 定位

SRS 采用持续演进模式：

```text
稳定业务事实与已验证需求 → 相对稳定
尚未验证的 AI 设计 → 明确标记假设
新增实践证据 → 逐步升级
被实践证伪的设计 → 允许修改或废弃
```

S2 形成业务与需求基线，不提前锁死模型、RAG、Agent、MCP 等技术实现；后续阶段持续深化。

## 3. 分阶段深化

| 阶段 | SRS 主要深化内容 |
|---|---|
| S1 | 产品问题、用户结果、AI适用性初判、机制边界 |
| S2 | 用户、角色、业务对象、状态、场景、规则、人机职责、异常、验收 |
| S3 | 模型任务、Input、Instruction、Structured Output、Schema、Validation、Eval |
| S4 | Context、知识、Retrieval、State、Memory、权限、生命周期 |
| S5 | Workflow、Agent、Tool、State、Stop、Retry、Human Approval |
| S6 | Identity、Delegation、Permission、Audit、Security、Trace、MCP |
| S7 | 需求—架构—实现—Eval—治理的一致性与正式 V1.0 |

## 4. AI Native 五问

所有重要 AI 候选需求至少回答：

1. **为什么需要 AI？**
2. **AI 具体负责什么，不负责什么？**
3. **AI 需要什么 Context？**
4. **AI 失败怎么办？**
5. **怎样证明它有效？**

这五问是需求设计的基本检查器，不代替后续模型、Context 和 Agent 的详细设计。

## 5. 业务需求与技术实现分离

例如：

> 家长需要获得符合当前阶段和家庭实际情况的成长重点。

属于业务需求。

> 使用 LLM Agent + 向量数据库生成成长任务。

属于当前实现假设。

业务需求可以稳定，AI 技术方案必须允许被实践证据修改。

## 6. 证据状态

关键 AI 设计建议标记：

```text
已验证 / 当前基线 / 假设 / 候选 / 废弃
```

避免 AI 生成的建议自动升级为正式需求。

## 7. GPT 与 Codex 边界

承担学习训练作用的重要需求，应优先由学习者形成首次判断，再由 GPT Review。

Codex 负责验证已确认需求的工程可实现性、测试和技术约束，不负责自行定义业务需求。

# 十、S1：整体认知与机制判断

## 1. 核心问题

> **AI Native 系统由哪些关键能力组成；面对一个真实任务，什么时候应该使用规则、传统程序、模型、Context、Workflow、Agent、Tool，什么时候不应该增加复杂度？**

## 2. 能力目标

重点达到 L1～L2：

- 能解释模型、Context、Knowledge、Workflow、Agent、Tool、Eval、治理之间的关系；
- 能区分规则、传统 Workflow、模型调用和 Agent；
- 能判断谁控制“下一步”；
- 能说明什么时候不用 Agent；
- 能识别明显过度设计；
- 能在陌生场景中进行基本机制选择。

## 3. 阶段运行方式

### 图

重建 AI Native 总体认知框架、六层功能架构、三条运行流及机制边界，并能从空白解释其关系。

### 拆

拆 3 个高质量 AI Native / Agentic System 案例和 1 个普通或过度设计案例，重点研究“为什么选择这种机制”。

### 练

通过多个短场景进行规则、模型、Context、Workflow、Agent、Tool 的机制判断，先独立作答，再 Review，只修一个主要判断错误。

### 用

以统一成长树中的首次进入、阶段判断、成长重点、月度建议、反馈和回看等场景进行 AI 适用性分析，不追求完整开发。

### 证

至少完成：

- 闭卷总体地图；
- 连续讲解；
- 未见场景机制选择；
- 一份真实任务说明。

## 4. 阶段成果

- AI Native 总体知识地图及迭代记录；
- 关键机制关系和案例拆解；
- 多个机制选择练习与错因记录；
- 统一成长树主要场景的 AI 适用性初步判断；
- 一份真实任务说明；
- 当前唯一主要弱点。

## 5. 阶段门禁

进入 S2 前至少满足：

- 能从空白重建整体结构；
- 能讲清 Workflow 与 Agent 的边界；
- 能解释什么时候不用 Agent；
- 能对陌生任务选择合理机制并说明理由；
- 能识别明显过度设计；
- 能把一个真实问题写成清楚、可验证的一页任务说明。

## 6. 不做范围

- 不开发完整统一成长树；
- 不固定模型、Agent Framework、向量数据库和云平台；
- 不系统实现 RAG、MCP 或 Multi-Agent；
- 不追求掌握全部 AI Native 术语。

S1 的核心成果是：

> **形成正确的 AI Native 整体判断框架。**

# 十一、S2：AI Native 需求深度学习工程

- 业务规则；

- 异常、风险和核心验收样例。

- 多个 AI 候选需求的五问分析；

- 一个非统一成长树场景的需求迁移练习。

## 4. 阶段成果

- 统一成长树产品定位与用户结果；
- 业务对象与状态模型；
- 用户旅程、场景、任务和规则；

## 5. 阶段门禁

- 产品解决的真实问题和主要用户结果清楚；
- 核心业务对象、关系和状态基本稳定；
- 主用户旅程能够闭环；
- 规则、AI 和人工职责能够区分；
- 核心 AI 候选需求能够完成五问；
- 技术实现没有冒充业务需求；
- 核心需求具有可执行验收样例；
- 已识别一个清楚、值得优先验证的最小模型任务。

## 6. 不做范围

- 不大规模编码；
- 不提前锁死模型、Prompt、RAG、Agent、MCP 和基础设施；
- 不要求 SRS 在本阶段达到最终 V1.0；
- 不让 GPT 直接替代核心需求判断。

S2 的核心成果是：

> **稳定业务需求基线 + 一个可验证的最小 AI 任务。**

# 十二、S3：模型应用、结构化输出与 Eval

## 1. 核心问题

> **怎样把一个概率性模型从“偶尔回答得不错”，建设成具有明确软件契约、失败处理和可重复质量证据的能力？**

## 2. 能力目标

重点达到 L2～L3：

- 能定义模型任务的输入、任务、约束、输出、成功与失败条件；
- 能区分 Instruction、Input、Context 和 Output；
- 能设计 Structured Output / Schema；
- 能处理格式错误、字段缺失、信息不足、拒绝、超时等基础失败；
- 能建立 Eval 数据集、Baseline 和 Failure Classification；
- 能通过同一 Eval 集进行版本比较。

## 3. 阶段运行方式

### 图

建立：

```text
业务任务
→ Model Task
→ Instruction / Input / 最小必要 Context
→ Model
→ Structured Output
→ Validation
→ Failure Handling
→ Eval
→ Failure Classification
→ Version Improvement
```

### 拆

比较 3 个可靠模型功能和 1 个只有演示效果、缺少 Schema / Validation / Eval 的普通 Prompt。

### 练

先保存未优化 Baseline，找到最主要失败类型，只修改一个主要变量，再用同一 Eval 集回归。

### 用

从 S2 选出的最小模型任务中实现统一成长树模型能力 V0.1。

V0.1 至少具备：

- 明确 Input；
- Instruction；
- Structured Output / Schema；
- Validation；
- 基础错误处理；
- 固定 Eval 样例；
- Baseline；
- 失败记录。

### 证

至少完成：

- 闭卷模型任务设计；
- 未见样例测试；
- Baseline 与修改版本对比；
- 一个“为什么相邻任务不应该交给模型”的反例。

## 4. 阶段成果

- 模型应用知识地图；
- 明确的模型任务说明；
- Input / Instruction / Output / Schema；
- Validation 和错误处理；
- 可运行或可评审的 V0.1；
- Eval 数据集、Baseline、失败分类；
- 至少一次基于证据的版本改进；
- 一个进入 S4 的主要 Context 缺口。

## 5. 阶段门禁

进入 S4 前至少满足：

- 能解释为什么当前任务需要模型；
- 输入、输出和边界明确；
- Structured Output 可以程序化验证；
- 基础无效输出能够被识别；
- Eval 可以重复运行；
- 失败样例被保留；
- 至少完成一次同 Eval 集版本对比；
- 面对未见输入能识别主要失败；
- 能区分 Prompt / Model 问题与 Context 问题。

没有 Eval Baseline 时，不进入复杂 Prompt、RAG 或 Agent 优化。

## 6. 不做范围

- 不追求 Prompt 技巧大全；
- 不一次开发多个 AI 功能；
- 不建设完整 RAG、Memory、Agent 或 Multi-Agent；
- 不使用复杂框架掩盖基础调用过程；
- 不允许 Codex 自动调 Prompt 后直接宣布优化成功。

S3 的核心成果是：

> **把一个模型任务建设成具有明确契约、失败处理和 Eval Baseline 的软件能力。**

# 十三、S4：Context、检索与可信知识

## 1. 核心问题

> **模型不知道、容易忘记、必须有依据且存在权限和生命周期约束的信息，怎样被正确、可信、受控地提供？**

## 2. 能力目标

重点达到 L2～L3：

- 能建立 Context Map；
- 能标记来源、Owner、可信度、时效、权限和生命周期；
- 能理解 Data → Retrieval → Selection → Assembly → Model 的全链路；
- 能区分数据、Retrieval、Assembly、Permission 和 Model 问题；
- 能区分会话 State、任务 State 和长期 Memory；
- 能证明 Context / Retrieval 是否真的改善结果。

## 3. 阶段运行方式

### 图

建立：

```text
业务任务
→ Context Need
→ Context Map
→ Data Source
→ Quality / Permission / Lifecycle
→ Retrieval / Selection / Assembly
→ Model
→ Citation / Result
→ Eval
```

并并行管理 Conversation State、Task State 和 Long-term Memory。

### 拆

拆 3 个可信知识或个性化 Context 案例和 1 个“只有向量搜索”的普通案例。

### 练

用固定 Eval 样例定位一个主要 Context 失败，只修改一个主要环节，再回归。

### 用

建立统一成长树 Growth Context Map，候选信息包括儿童状态、阶段、成长目标、家庭约束、历史观察、任务、反馈、兴趣、资源和成长知识。

Context 至少区分：

- 稳定 Context；
- 阶段 Context；
- 任务 Context；
- 历史 Context；
- 知识 Context。

Retrieval 选择优先比较：

```text
结构化读取
→ 数据库 / Metadata 查询
→ 关键词
→ 向量
→ 混合检索
```

能用更简单方案时不升级。

### 证

至少完成：

- 独立 Context Map；
- 无 Context / 基础 Context / 改进 Context 对比；
- Citation 与来源验证；
- 权限过滤测试；
- 未见失败的链路诊断。

## 4. 阶段成果

- Context Engineering 知识地图；
- Growth Context Map；
- 数据来源、Owner、权限和生命周期说明；
- Retrieval / Context Assembly 方案；
- State / Memory 边界；
- Context / Knowledge V0.2；
- Context Eval、Citation 和权限测试；
- 一个真正需要多步骤控制的问题。

## 5. 阶段门禁

进入 S5 前至少满足：

- 能解释 Context 不等于 RAG；
- 能建立完整 Context Map；
- 能说明重要 Context 的来源和生命周期；
- 能证明 Context / Retrieval 改善了结果；
- 重要知识判断可追溯到正确来源；
- 无权限信息不能进入 Context；
- 能区分 State 与 Memory；
- 能定位数据、Retrieval、Assembly、Permission 或 Model 层失败；
- 如果简单查询足够，能够主动放弃向量检索。

## 6. 不做范围

- 不默认建设向量数据库；
- 不把 RAG 当成 Context Engineering 全部；
- 不把所有历史都存成 Memory；
- 不把所有数据塞进 Prompt；
- 不让模型承担最终权限控制；
- 不因为检索成功就宣称 RAG 有效。

S4 的核心成果是：

> **能够正确决定模型需要知道什么，并以可信、最小、受权限控制的方式提供。**

# 十四、S5：Workflow、Agent 与受控 Tool

## 1. 核心问题

> **怎样让 AI 从“生成答案”走向“受控完成多步骤任务”，同时保持可追踪、可停止、可恢复和可人工接管？**

## 2. 能力目标

重点达到 L2～L4：

- 能在规则、单次模型和五种 Workflow Pattern 之间进行选择；
- 能解释 Agent Loop 以及“谁控制下一步”；
- 能设计 Tool Contract；
- 能设计 State、Retry、Timeout、Stop、Budget 和 Human Approval；
- 能处理 Tool Failure、Permission Denied、Duplicate Action、Partial Completion；
- 能使用 Trace 复盘完整执行；
- 能用证据判断 Agent 是否真的必要。

## 3. 阶段运行方式

### 图

建立：

```text
Business Task
→ Mechanism Selection
→ Workflow / Agent
→ State
→ Model Decision
→ Tool
→ Environment Feedback
→ Stop / Continue
→ Human Approval
→ Trace / Eval
```

并区分 Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer 与 Agent。

### 拆

拆研究型、编码型、办公/运营型系统各一个，再加入一个过度自治或控制不足案例。

### 练

只选择任务分解、Tool Schema、State、Retry、Stop、Human Approval 或 Failure Recovery 中一个主要弱点。

### 用

分析统一成长树：

```text
首次进入
→ 阶段判断
→ 月度方案
→ 周任务
→ 家庭执行
→ 反馈
→ 回看
→ 调整
```

逐步判断哪些步骤应使用规则、模型、Workflow、Agent、Tool 或 Human。

默认升级路径：

```text
确定性程序
→ 单次模型
→ 固定 Workflow
→ 动态 Workflow
→ 受控 Agent
```

只有固定 Workflow 的失败证据明确存在时才引入 Agent。

Tool 从只读、建议、草稿、可逆写入逐步升级到高风险动作，高风险和不可逆操作必须人工确认。

### 证

至少完成：

- 一个陌生多步骤任务的闭卷控制结构设计；
- Tool 正常、空结果、错误参数、超时、权限和重复请求测试；
- 一个失败 Trace 的完整复盘；
- Agent 必要性说明；
- 如果使用 Agent，同 Eval 集下与更简单方案的比较。

## 4. 阶段成果

- Workflow / Agent / Tool 控制地图；
- 机制选择决策树；
- Tool/API Contract；
- State、Retry、Timeout、Stop、Human Approval 规则；
- 可追踪、可停止、可恢复的 V0.3；
- Tool Failure 测试和 Trace；
- Agent 必要性结论；
- 一个进入 S6 的主要治理问题。

## 5. 阶段门禁

进入 S6 前至少满足：

- 能正确区分 Workflow 与 Agent；
- 能解释五种 Workflow Pattern；
- 能独立选择控制结构；
- Tool Contract 清楚并经过异常测试；
- 系统具有最大轮次、超时、预算或停止条件；
- 高风险操作有人工确认；
- 能沿 Trace 完整复盘失败；
- 如果使用 Agent，能够证明其必要性；
- 单 Agent 未暴露明确瓶颈时不进入 Multi-Agent。

## 6. 不做范围

- 不默认使用 Agent；
- 不把固定 Workflow 包装成 Agent；
- 不为了自主性取消人工控制；
- 不在无证据情况下进入 Multi-Agent；
- 不设计没有业务价值的 Tool；
- 不允许无限 Agent Loop；
- 不忽略 Tool 权限和幂等。

S5 的核心成果是：

> **能够设计一个受控、可恢复、可验证的多步骤 AI 执行系统。**

# 十五、S6：企业集成、MCP、治理与可观测

## 1. 核心问题

> **AI 获得企业数据和行动能力后，怎样做到能用、敢用、可观察、可追责？**

## 2. 能力目标

重点达到 L3～L4：

- 能建立 Capability Map；
- 能区分 Business Capability、API、Tool 和 MCP；
- 能理解 MCP Host、Client、Server、生命周期和授权边界；
- 能设计用户身份、Agent 委托、数据权限、Tool 权限和 Action 权限；
- 能设计 Approval、Audit、Human Takeover；
- 能处理 Prompt Injection、恶意文档、Tool Misuse、Data Leakage；
- 能建立模型、Context、Tool、State、人工、Token、Cost、Latency 的可观测链。

## 3. 阶段运行方式

### 图

建立：

```text
User / Identity
→ Agent Delegation
→ Capability
→ Permission
→ API / Tool / MCP
→ Business System
→ Approval / Audit
→ Observability
→ Security / Governance
```

横向贯穿 Eval、Security、Cost、Trace 和 Human Control。

### 拆

为一个真实 Capability 比较 Direct API、SDK/Adapter、Tool Wrapper 和 MCP，重点分析标准化、复用、安全、权限、维护和场景价值。

### 练

从 Permission、Approval、Audit、Prompt Injection、Human Takeover、Observability 中选择一个主要弱点，通过异常或攻击场景验证。

### 用

统一成长树用于训练家庭/儿童数据边界、AI建议边界、Memory、Tool 权限、确认和审计等基础治理能力。

同时必须增加至少一个企业 Capability 案例，建立：

```text
Capability
→ Identity
→ Permission
→ Tool
→ Approval
→ Audit
→ Trace
```

以补足企业组织、多级权限、高风险操作和审批场景。

### 证

至少完成：

- Capability Map；
- Permission Matrix；
- 至少一次越权 / Prompt Injection / Tool Failure / 高风险操作测试；
- MCP 使用或不使用的选型说明；
- 一次关键执行的 Trace + Audit 复盘。

## 4. 阶段成果

- Capability Map；
- API / Tool / MCP 边界说明和选型记录；
- Identity / Delegation 模型；
- Permission Matrix；
- Approval / Audit 设计；
- Threat Model 与安全测试；
- Observability / Trace 方案；
- Token / Cost / Latency 基线；
- 统一成长树 V0.4 / V0.5；
- 至少一个企业 Capability 治理案例。

## 5. 阶段门禁

进入 S7 前至少满足：

- Capability、API、Tool、MCP 边界清楚；
- 能说明什么时候不使用 MCP；
- 用户身份和 Agent 委托关系清楚；
- 数据权限与 Tool 权限有确定性控制；
- 高风险操作全部有人工确认；
- 测试中不得出现未授权读写；
- 关键动作有审计；
- 至少完成一次注入或越权测试；
- 关键执行可以沿 Trace 复盘；
- 能把成长树中的治理原则迁移到一个企业 Capability。

## 6. 不做范围

- 不为了 MCP 而建设 MCP；
- 不把 MCP 当成业务授权机制；
- 不让模型自己决定最终权限；
- 不开放没有确认、审计和回滚的高风险写操作；
- 不只依靠 Prompt 实现安全；
- 不为了可观测而保存不必要敏感信息；
- 不一次性建设完整企业 AI 平台。

S6 的核心成果是：

> **让 AI Native 系统从“能运行”走向“具备可信运行基础”。**

# 十六、S7：端到端产品化、企业迁移与个人方法论

## 1. 核心问题

> **在没有逐步教程的情况下，能否把一个真实 AI Native 问题从业务目标做到可验证结果，并解释所有关键取舍？**

## 2. 能力目标

重点达到 L3～L4：

- 能把业务、需求、模型、Context、Workflow/Agent、Tool、集成、Eval 和治理整合为一致系统；
- 能解释关键技术使用与不使用的理由；
- 能通过真实或脱敏案例、Eval、失败样例和用户反馈验证结果；
- 能迁移到此前未系统设计过的企业场景；
- 能形成自己的企业级 AI Native 解决方案方法论。

## 3. 阶段运行方式

### 图

从空白重新形成完整 AI Native 系统总图，并把统一成长树真实实现映射到图上。

### 拆

不再主要拆外部案例，而是把统一成长树当作陌生系统反向审查：

- 业务是否成立；
- 模型是否承担不必要工作；
- Context 是否过多、缺失或错误；
- Workflow / Agent 是否过度复杂；
- Tool 契约和权限是否清楚；
- Eval 是否真的证明价值；
- 最坏失败是什么；

### 练

根据 S1～S6 证据选择唯一最大弱点，进行 2～3 次同标准专项训练，不新增大型主题。

### 用

同时完成《统一成长树 AI Native 产品需求规格说明书 V1.0》。

### 证

必须完成三类证明：

1. **产品证明**：完整业务闭环、固定 Eval、未见样例、失败样例、真实或脱敏反馈、版本对比。
2. **个人能力答辩**：从空白解释业务、模型、Context、Workflow/Agent、Tool、Eval、权限、风险和成本。
3. **企业陌生场景迁移**：在此前未系统设计的企业问题上独立完成业务目标、AI Fit、需求、Context、机制、Tool、Eval、权限和最小架构。

## 4. 阶段成果

- 统一成长树 AI Native 产品 V1.0；
- 统一成长树 SRS V1.0；
- 端到端总体架构；
- 版本化 Eval 和失败分类；
- Context / Workflow / Agent / Tool / Governance 设计；
- 真实或脱敏案例反馈报告；
- 企业陌生场景迁移方案；
- 个人 AI Native 总知识地图；
- 《个人企业级 AI Native 解决方案方法论 V0.1》。

## 5. 最终门禁

V3.0 最终完成至少满足：

- 能独立完成一个端到端 AI Native 方案；
- 统一成长树存在可运行、可验证的核心闭环；
- 能解释为什么使用或不使用 Agent、RAG、MCP；

# 十七、时间投入与阶段推进模型

## 1. 时间的职责

V3.0 不再把“六个月”作为硬性目标。

采用：

```text
能力阶段推进
+ 有效投入管理
+ 阶段门禁决定升级
```

时间管理资源，证据决定完成。

## 2. 当前投入基线

- 日均 AI Native 深度工作预算：约 2 小时；
- 每周有效投入：约 10～12 小时；
- 总有效投入初步估算：约 340～450 小时；
- 参考周期：约 7～10 个月；
- 中心预估：约 8 个月。

这是规划假设，不是门禁。

## 3. 七阶段初始投入估算

| 阶段 | 有效投入估算 |
|---|---:|
| S1 | 35～45h |
| S2 | 50～70h |
| S3 | 40～55h |
| S4 | 50～65h |
| S5 | 55～70h |
| S6 | 50～65h |
| S7 | 60～80h |

如果阶段提前通过门禁，直接升级；如果超过估算但关键证据不足，则继续补唯一主要弱点。

## 4. 远粗近细

```text
远期：阶段能力与门禁
↓
当前：阶段执行计划
↓
本周：唯一重点
↓
当天：具体可执行任务
```

不提前生成 7～10 个月的固定每日计划。

## 5. 两小时不是固定课程时间

根据任务类型动态使用：

- 知识理解日：资料 + GPT讨论 + 闭卷；
- 需求学习日：知识补充 + SRS设计 + Review；
- 工程实践日：明确验证目标 + Codex + Test/Eval；
- 能力取证日：首次独立完成 + Review + 重做。

## 6. 时间异常处理

明显延期时优先诊断：

- 能力本身困难；
- 范围过大；
- 资料过多；
- 产品开发偏航；
- 工程复杂度过高；
- 低价值整理过多。

连续投入但没有新证据时，应缩小问题并设计最小练习，而不是无限阅读或开发。

# 十八、评测、证据与阶段门禁

## 1. 证据的意义

AI 辅助可以快速产生正确答案和工程结果，因此：

> **结果正确 ≠ 个人能力形成。**

V3.0 使用证据和阶段门禁判断真实能力状态。

## 2. 五类能力证明

| 能力 | 典型证明 |
|---|---|
| 能解释 | 闭卷地图、白板讲解、无资料口述 |
| 能判断 | 新场景选型、反例、复杂度对比 |
| 能实践 | 独立需求、设计、工程和项目增量 |
| 能验证 | Baseline、Eval、Trace、失败分类、版本对比 |
| 能迁移 | 陌生需求、陌生企业场景、新领域方案 |

## 3. 六类正式证据

- 知识证据；
- 判断证据；
- 产品证据；
- 工程证据；
- Eval 证据；
- 迁移证据。

不同阶段根据目标选择组合，不要求每次任务都产生全部证据。

## 4. 指标原则

候选指标包括：

- 任务完成率；
- Structured Output 有效率；
- Citation 正确率；
- Retrieval Recall / Noise；
- Tool Success Rate；
- 未授权读写次数；
- 人工直接采用 / 修改后采用 / 拒绝比例；
- Human Takeover；
- P50 / P95 Latency；
- Token 和单任务 Cost。

只有能改变设计、版本、上线、降级或风险决策的指标才值得保留。

## 5. Baseline 与失败样例

所有重要优化优先保存 Baseline。

失败样例至少记录：

```text
输入
→ 预期
→ 实际
→ 失败类型
→ 原因判断
→ 是否修复
```

修复成功后仍保留失败样例并进入回归。

## 6. 阶段门禁状态

### PASS

核心门禁全部满足，正式进入下一阶段。

### PARTIAL

总体能力已经建立，但关键证据尚未补齐。

**PARTIAL 不视为正式通过。** 可以提前接触下一阶段的 L1 认知，但主执行阶段仍停留在当前阶段，直到补证后转为 PASS。

### FAIL

关键能力证据不足，不进入下一阶段，只补当前唯一主要弱点。

## 7. AI 与能力证明

GPT 给出正确 Context Map、Codex 完成 Tool Calling、统一成长树可以运行，都只能证明系统形成了相应成果，不能自动证明个人能力达到对应等级。

GPT、Codex、课程或现成案例可以用于 Review、出题、反例、评分辅助和工程加速，但不能单独作为个人能力证据。个人能力必须通过独立解释、独立判断、首次实践、失败定位和陌生场景迁移来证明。

承担能力证明作用的关键任务，应尽可能保留首次独立版本。

# 十九、复杂度升级与停止规则

## 1. 复杂度升级路径

```text
确定性规则 / 传统程序
→ 单次或少量模型
→ Context / Retrieval / Tool 增强
→ 固定 Workflow
→ 动态 Workflow / Feedback Loop
→ 受控 Agent
→ 有充分证据时才考虑 Multi-Agent
```

## 2. 每次升级必须回答

1. 当前简单方案的失败证据是什么？
2. 新复杂度解决哪个具体失败？
3. 怎样比较新旧方案？
4. 增加了什么成本、延迟、安全和维护风险？
5. 如果无效，怎样退回简单方案？

## 3. 全局停止规则

- 没有明确业务任务，不增加 AI；
- 规则足够，不调用模型；
- 单次模型足够，不建设 Workflow；
- 固定 Workflow 足够，不使用 Agent；
- 单 Agent 没有明确瓶颈，不使用 Multi-Agent；
- 没有 Capability 和授权模型，不为了 MCP 建 MCP Server；
- 没有最小权限、确认、审计和回滚，不开放高风险写操作；
- 没有 Eval，不宣称新 Prompt、模型、RAG 或 Agent 更好；
- 新框架不能明显改善质量、速度、维护或可控性，不切换技术栈；
- 资料不能改变地图、判断、设计、实现或 Eval，不继续深挖。

## 4. 学习工具停止规则

学习网站、自动化系统和知识管理平台只有在真实效率问题已经出现且收益明确时才建设。

如果：

```text
工具开发成本 > 实际学习效率收益
```

则退回 Markdown、Git 和最小任务体系。

## 5. 统一成长树停止规则

如果产品功能：

- 与当前阶段无关；
- 只是为了“看起来完整”；
- Codex 可以做但自己无法判断；
- 无法建立 Eval；
- 需要提前进入尚未掌握的复杂技术；
- 持续挤压知识学习和能力取证；

则暂停扩张，并允许从完整实现降级为最小原型、设计或纸面推演。

# 二十、学习者、GPT 与 Codex 协作边界

## 1. 三方定位

```text
学习者 = 学习主体 + 最终决策者
GPT = 学习、架构与质量大脑
Codex = 工程执行与验证工具
```

## 2. 学习者负责

- 学习目标和优先级；
- 最终业务与架构判断；
- AI 适用性；
- 风险接受；
- 首次闭卷和关键练习；
- 产品方向；
- 证据可信度；
- 阶段是否真正完成。

## 3. GPT 负责

- 原理解释和知识结构化；
- 追问、反例、案例拆解；
- 需求和架构 Review；
- 专项练习、陌生迁移题和门禁检查设计；
- Codex TASK 编写；
- Codex 结果 Review；
- 阶段复盘和重复失败识别。

GPT 更接近：

> **教练 + 架构师 + Reviewer。**

承担训练作用的任务优先采用：

```text
学习者首次完成
→ GPT Review
→ 指出具体问题
→ 学习者重做
```

## 4. Codex 负责

- 阅读明确 TASK；
- 修改和编写代码；
- 执行命令；
- Debug；
- Test；
- Eval Execution；
- Trace；
- 工程结果记录。

Codex 不默认负责：

- 定义业务目标；
- 修改学习路线；
- 扩大产品范围；
- 决定是否需要 Agent；
- 决定核心架构；
- 把技术方案直接升级为正式需求。

遇到重大设计分支时，返回 GPT / 学习者完成判断。

## 5. Codex 介入程度

```text
S1 很少
S2 少量
S3 明显增加
S4 增加
S5 大量
S6 大量
S7 大量
```

是否使用 Codex 由任务性质决定，不由学习日决定。

## 6. 标准协作链

```text
学习者提出问题
→ GPT讨论 / 建模 / 设计
→ 学习者确认关键判断
→ 形成 TASK
→ Codex执行
→ Test / Eval / Trace
→ GPT Review
→ 学习者判断证据
→ PASS / 修订
```

模型可以变化，角色结构保持稳定。

# 二十一、当前执行状态与 V2.0 迁移规则

## 1. 迁移原则

V3.0 是结构升级，不清零 V2.0 已经形成的有效成果。

所有 V2.0 成果按四类迁移：

- **直接继承**：内容和证据仍有效；
- **需要补证**：知识已学习，但个人能力证据不足；
- **需要升级**：内容有效，但 V3.0 需要增加成长树映射或迁移；
- **历史保留**：被 V3.0 替代，但继续作为历史参考。

## 2. S1 迁移基线

V2.0 最后记录的状态（2026-08-28）为：

```text
D1 完成
D2 学习中 / 待补证
D3 学习中 / 待补证
```

V3.0 生效后的首个执行动作不是重新学习，而是：

```text
核验当前 D2 / D3 实际证据状态
→ 补齐仍未完成的证据
→ 更新 S1 当前状态
→ 继续既定 S1 路径
```

如果 D2 / D3 在 V3.0 定稿前已经完成，应以实际证据更新状态，不沿用旧记录。

## 3. V2.0 文档状态

V3.0 正式生效后：

```text
V3.0 = 当前权威战略总纲
V2.0 = historical reference / superseded
```

V2.0 不删除，用于版本历史、决策追溯和方法来源。

## 4. 学习不因规划重构暂停

任何后续 V3.x 优化都不得造成长期“只改学习系统、不实际学习”的状态。

规划改进必须服务执行，而不是替代执行。

# 二十二、版本升级规则

## 1. V3.x 小版本

适用于：

- 阶段时间估算变化；
- 局部能力目标调整；
- 统一成长树范围小幅变化；
- 门禁局部优化；
- 新实践证据要求局部调整路线。

前提是最终角色、三条主线、七阶段和学习方法没有根本变化。

## 2. V4.0 大版本

仅在以下情况考虑：

- 最终目标角色改变；
- 七阶段依赖被真实证据系统性否定；
- 统一成长树被证明不适合作为主实践项目；
- 能力模型需要根本调整；
- “图—拆—练—用—证—迭代”不再适用；
- 新实践证明当前学习系统存在结构性问题。

## 3. 不触发版本升级

新增课程、模型、论文、Prompt、Tool、阶段延期、Eval 指标变化和 Codex 工程结构变化，通常只进入阶段计划、Task、工程版本或复盘。

## 4. 版本变更记录

重要升级必须说明：

```text
改了什么？
为什么改？
证据是什么？
影响哪些阶段？
哪些已有内容仍有效？
```

# 二十三、最终共识

V3.0 最终冻结以下原则：

1. **目标由能力定义，不由时间定义。** 最终目标是企业级 AI Native 解决方案架构与落地能力。
2. **时间是资源，不是门禁。** 日均约 2 小时、参考周期约 7～10 个月，但阶段是否完成由证据决定。
3. **知识与能力主线、统一成长树实践主线和个人能力证据主线同时运行。** 同一次投入尽量同时形成认知、产品和证据。
4. **统一成长树是贯穿式真实实践主项目，不是最终学习目标。** 最终必须完成企业陌生场景迁移。
5. **SRS 是 AI Native 需求深度学习载体。** 业务需求与当前 AI 技术方案分离，SRS 随能力与证据逐步深化。
6. **复杂度只由失败证据驱动升级。** Rule → Model → Context/Tool → Workflow → Agent → Multi-Agent，能用简单方案时不升级。
7. **没有 Baseline、失败样例和 Eval，不宣称方案变好。** Eval、Trace、权限、安全和人工控制是系统设计的一部分。
8. **GPT 负责帮助想得更深，Codex 负责帮助做得更快，学习者负责最终判断和能力证明。**

整个 V3.0 的运行模型为：

```text
                最终目标
     企业级 AI Native 解决方案架构者
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
     学知识      做真实产品     留能力证据
        │           │           │
 AI Native体系   统一成长树     L1 → L4
        │           │           │
        └───────────┼───────────┘
                    │
        图 → 拆 → 练 → 用 → 证 → 迭代
                    │
                    ▼
                阶段门禁
                    │
                    ▼
S1 整体认知与机制判断
        ↓
S2 AI Native 需求深度学习工程
        ↓
S3 模型应用、结构化输出与 Eval
        ↓
S4 Context、检索与可信知识
        ↓
S5 Workflow、Agent 与受控 Tool
        ↓
S6 企业集成、MCP、治理与可观测
        ↓
S7 产品化、企业迁移与个人方法论
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
成长树 V1.0     SRS V1.0     方法论 V0.1
                    │
                    ▼
               企业场景迁移
```

最终判断标准不是：

> 看了多少、写了多少、做了多少。

而是：

> **能否独立解释、判断、实践、验证，并把方法迁移到新的真实问题。**
