# AI Native 六个月系统学习与实践总纲 V2.0

> 本文件是个人 AI Native 六个月学习项目的权威战略总纲。
>
> 它定义六个月最终目标、能力路线、主项目演进、每月主题、阶段门禁和证据标准；不替代月度执行手册，也不提前制作僵硬的 24 周每日计划。

---

## 一、权威声明与使用方式

### 1. 内容源规则

从 V2.0 开始，正式采用：

```text
Markdown = 唯一权威内容源
Word = 从 Markdown 生成的阅读、打印和发布版本
Learning OS 界面 = Markdown 的任务化投影
Git = 版本、差异、审查与跨设备同步机制
```

修改规则：

1. 所有内容修改先发生在本 Markdown 文件。
2. 修改经过审阅并更新版本信息。
3. 需要正式阅读或分享时，由 Markdown 生成同版本 Word。
4. Word 发布版不再单独编辑，避免 Word 与 Markdown 内容漂移。

### 2. 文档权威层级

```text
第1层：Learning OS 上位运行共识
└── content/system/个人_AI_Native_Learning_OS_产品与学习运行模型_V0.1.md

第2层：六个月战略总纲
└── content/plans/six-month/AI_Native_六个月系统学习与实践总纲_V2.0.md（本文件）

第3层：月度执行手册
├── content/plans/month-01/第1月_完整执行指导手册_V2.0.md（正文版本 V2.1）
├── 第2月_完整执行指导手册_*.md
└── ……

第4层：周、日任务与学习成果
└── 知识地图、案例、练习、真实任务、项目增量

第5层：能力证据与复盘
└── 闭卷记录、测试、Evals、项目结果、日/周/月复盘
```

出现冲突时，按照以下规则处理：

- 学习运行原则以 Learning OS 上位共识为准。
- 六个月方向和月份依赖以本总纲为准。
- 当月的具体资源、任务、时间和验收以当月执行手册为准。
- 实际能力状态以成果和证据为准，不以手工勾选或文件数量为准。

### 3. 本总纲怎样使用

每月开始前：

- 查看本总纲中该月的能力目标、项目增量和阶段门禁。
- 根据上月证据生成或修订当月执行手册。
- 不直接把本总纲拆成固定的每日任务。

每周开始前：

- 选择一个服务于当月里程碑的唯一重点。
- 明确本周要形成的成果和证据。

每天执行时：

- 只使用当前月度手册和当天任务。
- 不在每天重复阅读六个月总纲。

每月结束时：

- 用证据判断是否通过阶段门禁。
- 根据唯一弱点决定下月第一个练习。
- 只有方向或能力结构发生变化时才更新本总纲。

## 二、六个月核心目标

### 1. 目标角色

六个月的目标不是成为大模型算法研究员，也不是追逐所有 Agent 框架，而是形成以下角色能力：

> **企业级 AI Native 解决方案架构者：能够把真实业务问题转化为受控、可验证、可集成、可治理并能够持续演进的 AI Native 系统。**

这一方向结合个人已有的企业平台、产品规划、流程、权限治理、系统方案和跨系统协同经验，重点补齐 AI Native 的模型应用、Context、Workflow、Agent、Tool、评测和治理能力。

### 2. 六个月后的目标状态

六个月后应能够：

1. 从业务结果出发，判断一个任务应使用规则、传统工作流、单次或少量模型、Workflow、Agent，还是混合架构。
2. 解释业务、交互、任务协调、Context、知识、模型、工具、企业系统、运行基础设施、评测和治理之间的关系。
3. 设计 Instruction、Context、Retrieval、State、Tool、Human Approval、Evaluation 和 Observability 的完整执行链。
4. 借助编程 Agent 完成可运行原型，同时能读懂关键代码、接口、日志、测试和失败结果。
5. 建立版本化 Evals、失败分类和回归机制，用证据判断方案是否真正改善结果。
6. 把身份、权限、数据范围、委托、审批、审计、幂等、回滚和人工接管纳入设计。
7. 用真实或脱敏案例证明系统的业务价值、可靠性、成本和适用边界。
8. 形成个人《企业级 AI Native 解决方案方法论 V0.1》和一个端到端可演示项目。

### 3. 不作为六个月主线

- 大模型预训练、底层算法研究和大规模参数训练。
- 为追热点而学习全部框架、SDK、模型和云产品。
- 脱离业务问题的 Prompt 技巧收集。
- 没有评测和使用场景的 Demo 堆积。
- 为了使用 Agent、Multi-Agent 或 MCP 而增加复杂度。
- 在证据不足时提前锁死第 2—6 月的每日任务。

## 三、“系统掌握”的能力标准

### 1. 五级能力状态

| 等级 | 状态 | 判断标准 | 典型证据 |
|---|---|---|---|
| L0 | 未进入 | 尚未安排或只知道名称 | 无 |
| L1 | 能解释 | 能用自己的话说明定义、位置、关系和基本原理 | 学习总结、知识地图、四问学习卡 |
| L2 | 能判断 | 能说明适用、不适用、主要权衡和复杂度选择 | 案例对比、反例、方案选择、迁移题 |
| L3 | 能实践 | 能在练习或项目中正确使用，并处理常见失败 | 代码、案例、测试、调试和项目增量 |
| L4 | 能验证与改进 | 能建立评测标准，定位失败并持续优化 | Evals、Trace、指标、对比实验、复盘报告 |

### 2. 六个月目标分层

- 核心能力：达到 L3 或 L4。
- 重要支撑能力：达到 L2 或 L3。
- 扩展认知：达到 L1 或 L2。

不是所有术语都需要达到同一深度。优先级由当前月份、主项目和真实证据决定，不由知识地图中的节点数量决定。

### 3. 核心节点完成条件

一个核心知识或工程节点至少需要：

```text
能够解释
+ 能够判断使用边界
+ 一个适用案例
+ 一个不适用案例或反例
+ 一次练习或项目使用
+ 一项可复查证据
```

## 四、六条长期能力主线

六个月按月份推进，但以下六条能力主线贯穿始终。

| 能力主线 | 必须掌握 | 最终能力证明 |
|---|---|---|
| 业务与产品 | 场景价值、用户结果、任务边界、AI 适用性、风险与 ROI 假设 | 用例卡、任务说明、PRD、价值与风险判断 |
| 模型应用 | Instructions、Prompt、Structured Output、模型选择、错误处理、成本与延迟 | 可复用模型功能、样例集、模型和 Prompt 对比 |
| Context 与知识 | 数据来源、检索、组装、引用、权限过滤、状态、Memory 和生命周期 | Context Map、检索评测、引用与权限证据 |
| Workflow / Agent / Tool | 模式选择、任务状态、路由、重试、幂等、停止条件、人工确认和工具契约 | 可追踪、可停止、可恢复的任务执行链 |
| 工程与评测 | 数据集、基线、自动评测、人工评审、Tracing、回归和版本管理 | Eval 集、失败分类、测试和版本对比报告 |
| 企业治理与安全 | 身份委托、最小权限、审批、审计、提示注入防护、数据边界和人工接管 | 权限矩阵、威胁模型、控制措施和审计证据 |

治理与评测不是最后才增加的附加模块：

- 第 1 月建立判断和证据意识。
- 第 2 月建立最小 Eval 基线。
- 第 3—4 月随 Context、Tool 和 Agent 增加相应控制。
- 第 5 月进行系统化治理、可观测和成本加固。

## 五、统一学习运行闭环

六个月中的每一个主题都运行完整闭环：

```text
图 → 拆 → 练 → 用 → 证 → 迭代
```

### 1. 图：建立位置和关系

回答：

- 它解决什么问题？
- 核心概念是什么？
- 在六层架构和三条流中的位置是什么？
- 与上下游能力怎样连接？
- 怎样判断它做得好？

产出：一张可以持续修订的知识或架构地图。

### 2. 拆：理解优秀成果为何成立

- 拆 3 个优秀案例。
- 加入 1 个普通案例或失败案例。
- 识别关键决策、证据、反例和失效条件。

产出：可追溯的案例记录和关键规律。

### 3. 练：只解决一个弱点

```text
小任务
→ 独立完成
→ 获得具体反馈
→ 只修改一个问题
→ 再做一次
```

产出：同一标准下可比较的前后练习证据。

### 4. 用：进入主项目或真实任务

- 把知识放进真实或脱敏问题。
- 形成一个可运行、可评审或可验收的增量。
- 明确有效条件、无效条件和不做范围。

产出：项目增量、任务说明、代码、设计或案例。

### 5. 证：离开资料证明能力

每月根据主题选择以下证据：

- 能画出来。
- 能讲清楚。
- 能独立做成。
- 能迁移应用。
- 能通过测试或 Evals 验证。

### 6. 迭代：证据决定下一步

只回答：

```text
哪里不好？
→ 证据是什么？
→ 为什么？
→ 下一次只改什么？
→ 通过标准是什么？
```

## 六、贯穿六个月的主项目

### 1. 主项目不是提前指定，而是证据选择

第一个月 D15 从多个真实问题中评分选择候选，D20 再根据整月证据决定第 2—6 月是否继续。

候选需要满足：

- 有明确用户和业务结果。
- 能持续获得真实或脱敏材料。
- 包含非结构化信息或需要判断的部分。
- 可以逐步承载模型、Context、Workflow、Agent 和 Tool。
- 风险可控，能够从只读或建议模式开始。
- 能够使用样例、测试、人工反馈或指标验证。

### 2. 推荐候选

“AI Native 企业项目治理助手”是优先候选，因为它能够结合：

- 项目资料、制度、合同、周报/月报和风险记录。
- 企业平台、流程、身份权限和审计经验。
- 模型理解、Context、Workflow、Agent、Tool 和治理能力。

但它在 D15/D20 证据确认前不是强制主项目。

### 3. 主项目版本演进

```text
第1月：选择问题并形成可验证任务说明，不开发完整产品
第2月：模型应用与结构化输出 V0.1
第3月：Context、检索与可信证据 V0.2
第4月：Workflow、Agent 与受控 Tool V0.3
第5月：企业集成、MCP、治理与可观测 V0.4 / V0.5
第6月：产品化、真实验证与方法论 V1.0
```

如果第一个月证据表明候选不适合继续，可以更换主项目；一旦进入第 2 月，除非价值、数据或风险假设被证伪，不轻易切换场景。

## 八、第1月：整体认知与机制判断

### 1. 本月目标

建立一套可以离开资料使用的 AI Native 判断框架：

- 从业务结果出发理解模型、Context、知识、工具、Workflow、Agent、评测和治理的关系。
- 判断什么时候不用 Agent。
- 把一个真实问题写成可验证的一页任务说明。

### 2. 权威执行依据

第一个月的具体 20 天任务、官方资源、时间、产出和验收全部以以下文件为准：

- `content/plans/month-01/第1月_开始这里.md`
- `content/plans/month-01/第1月_完整执行指导手册_V2.0.md`，正文版本 V2.1
- `content/plans/month-01/第1月_每日学习资源与产出路径.md`

本总纲不重复 D1—D20，避免产生第二套任务规则。

### 3. 本月路径

```text
第1周：图——整体结构、机制边界和质量标准
第2周：拆——3 个优秀案例 + 1 个普通 FAQ
第3周：练——首测、错因、专项练习、复测和候选问题
第4周：用、证、迭代——任务说明、闭卷、迁移和复盘
```

### 4. 本月不做

- 不开发完整产品。
- 不选择固定框架、模型供应商、向量数据库或云平台。
- 不学习模型训练和微调实现。
- 不追求完成全部 AI Native 术语。
- 不因为案例叫 Agent 就默认自己的方案需要 Agent。

### 5. 月末门禁

必须用工程中的实际成果证明：

- 15 分钟闭卷地图包含五问、六层、三条流和不用 Agent 的边界。
- 能连续讲 10 分钟并回答三个“为什么”。
- 能从空白完成真实任务说明和 5 个验收样例。
- 能对 3 个陌生场景选择机制并说明理由。
- 只选择一个下一弱点，并设计小于 90 分钟的第 2 月首个练习。

未通过时不增加新资料，只补唯一弱点。

## 九、第2月：模型应用、结构化输出与 Eval 基线

### 1. 核心问题

> 怎样把概率性的模型输出变成可以被软件消费、测试和持续改进的能力？

### 2. 能力目标

- 把业务任务写成明确输入、输出、约束和成功标准。
- 理解 Instructions、Prompt、示例、Structured Output 和 Schema 的职责。
- 处理无效输出、缺失字段、格式错误、拒绝和不确定结果。
- 比较简单规则、传统方法、不同 Prompt 或模型方案。
- 建立第一套版本化 Eval 数据集、基线和失败分类。

### 3. 建议四周节奏

#### 第1周：图与基线

- 画出任务、Instructions、Context、Model、Structured Output、Validation、Retry 和 Eval 的关系。
- 为主项目选择一个最小模型能力，例如抽取、分类、路由、总结或结构化风险识别。
- 准备第一批真实或脱敏样例，并保存未优化基线。

#### 第2周：拆与比较

- 拆 3 个可靠模型功能和 1 个只有演示效果的普通 Prompt。
- 比较任务定义、输入数据、Schema、校验、失败处理和评测差异。

#### 第3周：练与 V0.1

- 只选择一个主要失败类型进行专项练习。
- 完成主项目模型功能 V0.1。
- 保留输入、输出、失败、修订和回归结果。

#### 第4周：证与迭代

- 闭卷重新设计同类任务。
- 使用未见样例测试迁移能力。
- 形成失败分类和版本对比。
- 只选择第 3 月需要优先解决的 Context 问题。

### 4. 本月成果

- 模型应用层知识地图及迭代版本。
- 任务说明、Schema 和错误处理规则。
- 可运行或可评审的模型功能 V0.1。
- 初始 Eval 数据集、评分规则和失败分类。
- 基线与改进版本对比报告。

### 5. 月末门禁

- 能解释为什么这部分需要模型，而不是确定性程序。
- 输出能够通过程序化格式和关键字段检查。
- Eval 可以重复运行，失败样例得到保留。
- 面对未见输入时，能够识别主要失败类型。
- 没有 Eval 基线时，不进入复杂 Prompt、RAG 或 Agent 优化。

## 十、第3月：Context、检索与可信知识

### 1. 核心问题

> 模型不知道的、容易忘的、必须有依据且受权限约束的信息，怎样被正确提供？

### 2. 能力目标

- 建立用户、组织、业务对象、历史、制度、文档、权限和任务状态的 Context Map。
- 理解数据清洗、解析、分块、元数据、索引、检索、重排和上下文组装。
- 区分检索质量、Context 质量和生成质量。
- 建立引用、来源追溯、冲突提示、缺失信息澄清和权限过滤。
- 理解会话状态、任务状态和长期 Memory 的不同用途与生命周期。

### 3. 建议四周节奏

#### 第1周：Context Map

- 标记每类信息的来源、Owner、时效、可信度、权限和生命周期。
- 明确什么必须进入 Context，什么不应该进入。

#### 第2周：案例与检索基线

- 拆 3 个可信知识型成果和 1 个只做向量搜索的普通案例。
- 使用固定问题集比较无检索、关键词/元数据检索、向量或混合检索。

#### 第3周：专项练习与 V0.2

- 只选择切分、召回、重排、上下文选择、引用或权限中的一个主要弱点。
- 将主项目升级到 V0.2。

#### 第4周：证据与回归

- 使用未见问题诊断失败发生在哪一层。
- 比较有无 Context 改进的结果。
- 记录来源错误、权限错误、没有找到、找到但没用好等失败类别。

### 4. 本月成果

- Context Map。
- 数据来源、权限和生命周期说明。
- 检索与 Context 组装方案。
- 可运行的 Context/RAG V0.2。
- 检索、引用和生成评测报告。

### 5. 月末门禁

- 能证明 Context 或检索确实改善了结果，而不是只完成向量库搭建。
- 重要判断可以追溯到正确来源。
- 越权信息不能进入 Context。
- 能对新失败判断问题发生在数据、检索、组装还是生成环节。
- 不能证明检索有价值时，保留更简单方案。

## 十一、第4月：Workflow、Agent 与受控工具

### 1. 核心问题

> 怎样让 AI 不只回答，而是安全、可控、可停止、可恢复地完成多步任务？

### 2. 能力目标

- 区分规则、单次模型、固定 Workflow、五种 Workflow Pattern 和 Agent。
- 掌握 Prompt Chaining、Routing、Parallelization、Orchestrator-Workers 和 Evaluator-Optimizer。
- 理解 Agent Loop、任务状态、计划、工具选择、环境反馈和完成判断。
- 设计清晰的 Tool 名称、参数、返回、错误码、权限和幂等规则。
- 建立超时、重试、最大轮次、预算、取消、停止和人工接管。
- 使用 Trace 复盘一次完整执行。

### 3. 建议四周节奏

#### 第1周：控制结构与模式选择

- 画出规则、Workflow、Agent、Tool、State、Environment Feedback 和 Human Approval 的控制关系。
- 为主项目建立机制选择决策树。

#### 第2周：拆 Agentic System

- 拆研究、编码、运营/办公 3 个优秀多步系统。
- 加入 1 个无状态、无停止或过度自治的普通案例。
- 区分模式名称和实现组件，避免把 Planner、Router、Orchestrator 与五种 Workflow 并列。

#### 第3周：专项练习与 V0.3

- 选择任务分解、工具契约、状态、失败恢复或停止条件中的一个弱点。
- 先实现最简单 Workflow；只有证据证明总体路径无法预定时才引入 Agent。
- 将主项目升级到 V0.3。

#### 第4周：验证 Agent 必要性

- 在同一 Eval 集上比较简单方案和复杂方案。
- 测试空结果、错误参数、工具失败、超时、重复执行、权限不足和人工接管。
- 使用 Trace 解释失败发生在哪里。

### 4. 本月成果

- Workflow / Agent / Tool 控制地图。
- 模式选择决策记录。
- Tool/API 契约与测试。
- 可追踪、可停止、可恢复的主项目 V0.3。
- 简单方案与复杂方案的质量、成本、延迟和风险对比。

### 5. 月末门禁

- 能明确解释为什么需要 Agent；如果不能，退回 Workflow。
- 工具调用经过参数、异常、空结果、权限和幂等测试。
- 系统有最大轮次、超时、预算和人工接管。
- 一个失败案例能够沿 Trace 完整复盘。
- 单 Agent 没有暴露明确瓶颈时，不引入 Multi-Agent。

## 十二、第5月：企业集成、MCP、治理与可观测性

### 1. 核心问题

> AI 获得企业数据和行动能力后，怎样做到能用、敢用、可观察、可追责？

### 2. 能力目标

- 建立企业 Capability Map，区分查询、建议、创建、审批、变更和高风险操作。
- 先设计业务能力和 API/Tool 契约，再判断是否使用 MCP。
- 理解 MCP Host、Client、Server、生命周期、能力协商和授权边界。
- 建立用户身份、Agent 委托、数据权限、工具权限、动作权限和审批链。
- 系统化处理提示注入、恶意文档、工具误选、数据泄漏、越权和冲突信息。
- 建立模型、Context、Tool、状态、人工介入、Token、延迟和成本的可观测链。

### 3. 建议四周节奏

#### 第1周：Capability 与信任边界

- 画出用户身份、Agent、Context、Tool/API/MCP、企业系统、审批、审计和人工接管。
- 为每项能力标记 Owner、数据边界、风险等级和授权方式。

#### 第2周：MCP 与普通 API 对比

- 拆 MCP 的稳定原理，不把协议等同于业务授权。
- 为主项目选择一个能力，比较直接 API、SDK/Adapter 和 MCP 的复杂度与价值。

#### 第3周：治理专项练习与 V0.4

- 只选择权限、审批、审计、注入防护或人工接管中的一个主要弱点。

- 将主项目升级到 V0.4。

#### 第4周：可观测与加固 V0.5

- 加入 Eval 门禁、Tracing、日志、成本、延迟、降级和回滚。
- 运行越权、注入、工具失败和高风险操作测试。
- 比较治理加固对质量、成本和使用体验的影响。

### 4. 本月成果

- 企业 Capability Map。
- API/Tool 契约和 MCP 选型说明。
- 身份委托与权限矩阵。
- 审批、审计、人工接管和威胁模型。
- Tracing、成本、延迟和回归报告。
- 企业级主项目 V0.4/V0.5。

### 5. 月末门禁

- Capability、API、Tool 和 MCP 的边界清楚。
- 高风险或不可逆动作全部经过明确人工确认。
- 测试集中不得出现未授权读取或写入。
- 关键执行可以沿 Trace 和审计记录复盘。
- 没有最小权限、确认、审计和回滚时，不开放真实写操作。

## 十五、评测、证据和指标

### 1. 学习能力证据

| 能力 | 通过动作 | 判断重点 |
|---|---|---|
| 能解释 | 闭卷地图和口头讲解 | 不堆术语，能说明关系和因果 |
| 能判断 | 新场景选型和反例分析 | 能说明适用、不适用和权衡 |
| 能实践 | 独立完成练习或项目增量 | 无逐步教程仍能达到预设标准 |
| 能验证 | Evals、Trace、指标和对比实验 | 能定位失败并证明改进有效 |
| 能迁移 | 在陌生领域形成最小方案 | 方法不依赖做过的原题 |

### 2. 项目质量指标

项目指标必须结合真实场景校准。以下是候选指标，不是尚未验证就永久固定的数字：

- 任务完成率。
- 结构化字段完整率和有效率。
- 证据或引用正确率。
- 检索召回、噪声和错误类型。
- Tool 成功率、失败可解释性和重试结果。
- 未授权读取、写入和高风险动作发生次数。
- 人工直接采用、小改采用和拒绝比例。
- P50/P95 延迟、Token 和单任务成本。
- 人工接管频率与接管原因。

### 3. 指标使用原则

- 先保存基线，再优化。
- 同一版本使用同一 Eval 集比较。
- 同时保存平均结果和失败样例。
- 不能只优化离线分数而损害用户结果、安全或成本。
- 指标没有决策用途时，不为了“看起来专业”而增加。

## 十六、复杂度升级和停止规则

### 1. 复杂度升级路径

```text
确定性规则或传统程序
→ 单次/少量模型
→ 增强型模型：Context / Retrieval / Tools
→ 固定 Workflow
→ 带动态子任务或反馈循环的 Workflow
→ 受控 Agent
→ 只有证据证明必要时才考虑 Multi-Agent
```

每次升级必须回答：

- 当前简单方案的失败证据是什么？
- 新复杂度具体解决哪个失败？
- 怎样比较新旧方案？
- 增加了什么成本、延迟、安全和维护风险？
- 如果无效，怎样退回简单方案？

### 2. 停止规则

- 没有明确业务任务，不增加 Agent。
- 规则、检索、单次模型或固定 Workflow 已经足够时，不升级自治能力。
- 没有 Eval 基线，不宣称新 Prompt、模型、RAG 或 Agent 更好。
- 单 Agent 没有暴露明确瓶颈，不引入 Multi-Agent。
- 没有业务 Capability 和授权模型，不为了使用 MCP 建设 MCP Server。
- 没有最小权限、确认、审计和回滚，不开放写操作。
- 新框架不能明显改善质量、速度或维护性，不切换技术栈。
- 资料不能改变地图、设计、实现或评测，只进入候选资料库。
- 一次学习超过时间上限仍无结果，保存当前版本和卡点，不无限阅读。

## 十七、AI 与学习者的协作边界

### AI 可以承担

- 把月度目标转成周、日任务草案。
- 解释概念、提供对比和反例。
- 设计针对唯一弱点的练习。
- 根据明确标准评审总结、方案、代码和证据。
- 汇总计划和实际偏差，发现重复失败模式。

### AI 不应代替

- 首次闭卷版本。
- 最终业务和架构判断。
- 关键练习和真实实践。
- 对证据可信度的最终判断。
- 计划优先级和风险接受决定。

每次 AI 反馈只解决一个具体问题，并采用：

```text
哪里不好
→ 为什么
→ 下一次只改什么
```

AI 生成了一份完整答案，不代表学习者已经掌握。

## 二十一、最终共识

> 六个月学习不是依次看完六组知识，而是围绕一个由证据选择的真实问题，连续完成六次“图—拆—练—用—证—迭代”闭环。

> 第一个月建立整体判断并选择问题；第二个月把模型能力做成可评测功能；第三个月让系统获得可信且受权限约束的 Context；第四个月建立可控的 Workflow、Agent 和 Tool；第五个月完成企业集成、MCP、治理和可观测；第六个月把所有能力整合成可演示、可验证、可迁移的端到端成果与个人方法论。

> 学习进度不由文件数量和页面状态证明，而由能否解释、判断、实践、验证和迁移的证据证明。
