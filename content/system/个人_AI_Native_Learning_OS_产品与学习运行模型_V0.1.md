# 个人 AI Native Learning OS 产品与学习运行模型 V0.1

> 本文档是六个月 AI Native 学习项目的上位共识。
>
> 它不替代六个月规划、月度计划、执行指导手册、知识地图和每日学习总结，而是规定这些内容如何共同组成一个可以持续运行、形成成果并验证能力的个人学习系统。

---

## 一、一页共识

### 1. 核心目标

在六个月内系统掌握 AI Native，不以“看过多少资料”或“记录多少知识点”为完成标准，而以以下能力是否形成并有证据支持为标准：

1. 能解释 AI Native 的核心概念、架构和运行机制。
2. 能根据业务问题选择合适的模型、Workflow、Agent、知识、工具和运行方案。
3. 能独立设计、实现、调试一个端到端 AI Native 系统。
4. 能用 Evals、日志、追踪、测试和业务指标判断系统是否有效。
5. 能沉淀可复用的设计方法、案例、代码、文档和决策依据。

### 2. Learning OS 的定位

Learning OS 不是知识管理网站，也不是 Markdown 阅读器。

它是：

> **六个月 AI Native 学习计划的个人执行、记录、验证与复盘系统。**

### 3. 系统中各类内容的职责

- 六个月规划：定义方向和最终能力。
- 月度计划：定义阶段目标和里程碑。
- 执行指导手册：定义学习规则、方法和完成标准。
- 周计划：选择本周需要推进的能力和任务。
- 每日任务：构成实际执行单元。
- 知识地图：组织学习内容及其关系。
- 节点学习卡：完成单个知识节点的理解与边界判断。
- 案例、练习和项目：把理解转化为应用能力。
- 证据：证明能力已经形成。
- 复盘：根据结果调整后续计划。
- 界面：把上述系统投影成每天容易执行的工作台。

### 4. 最核心的运行关系

```text
六个月目标
    ↓
月度里程碑
    ↓
周计划
    ↓
每日学习任务
    ↓
相关知识节点
    ↓
学习、练习与真实应用
    ↓
成果与验证证据
    ↓
日 / 周 / 月复盘
    ↓
调整后续计划
```

### 5. 一句话运行原则

> **计划负责驱动学习，知识地图负责定位内容，学习任务负责产生行为，成果与证据负责证明掌握，复盘负责修正计划。**

## 二、为什么需要 Learning OS

六个月学习项目面临的主要问题不是资料不足，而是以下内容容易彼此割裂：

- 总体目标与每天行动割裂。
- 月度计划与知识地图割裂。
- 学习总结与实践任务割裂。
- 文件数量与真实能力割裂。
- 当天学习与后续计划割裂。
- AI 对话与工程中的长期成果割裂。

Learning OS 的价值不是增加一个界面，而是建立稳定的转换关系：

```text
目标 → 计划
计划 → 任务
任务 → 知识
知识 → 实践
实践 → 成果
成果 → 证据
证据 → 复盘
复盘 → 新计划
```

只要其中一个转换关系缺失，学习系统就会退化：

- 只有目标没有任务：计划无法执行。
- 只有知识没有实践：形成知识收藏。
- 只有实践没有知识结构：经验难以迁移。
- 只有成果没有证据：无法判断是否掌握。
- 只有记录没有复盘：记录不能改善计划。

## 三、“系统掌握 AI Native”的定义

### 1. 掌握不等于接触

本项目不使用简单的“未学习 / 已学习”二元状态，而使用五级能力状态：

| 等级 | 状态 | 判断标准 | 典型证据 |
|---|---|---|---|
| L0 | 未进入 | 尚未安排或只知道名称 | 无 |
| L1 | 能解释 | 能用自己的话说明定义、位置和基本原理 | 学习总结、四问学习卡 |
| L2 | 能判断 | 能说明适用条件、不适用条件和主要权衡 | 对比分析、反例、方案选择记录 |
| L3 | 能实践 | 能在练习或项目中正确使用，并能处理常见问题 | 代码、案例、测试结果、调试记录 |
| L4 | 能验证与改进 | 能建立评价标准，定位失败原因并持续优化 | Evals、实验对比、指标、复盘报告 |

### 2. 节点“完成”的条件

知识节点不因为阅读结束或写过总结而完成。

一个核心知识节点至少需要：

```text
四问学习卡
+ 一个适用案例
+ 一个不适用案例或反例
+ 一次练习或真实任务
+ 一项可复查证据
```

辅助节点可以降低实践强度，但必须能够说明它与核心节点的关系。

### 3. 六个月后的目标状态

六个月后的“系统掌握”不要求所有节点达到同一深度，而采用分层目标：

- 核心能力节点：目标达到 L3 或 L4。
- 重要支撑节点：目标达到 L2 或 L3。
- 扩展认知节点：目标达到 L1 或 L2。
- 至少形成一个可以完整展示和复盘的端到端 AI Native 项目。
- 能从业务目标出发，独立完成架构选择、实现、评估和迭代，而不是只能复述术语。

具体哪些节点属于核心、重要或扩展，由六个月计划和月度计划定义，知识地图本身不决定优先级。

## 四、Learning OS 的产品北极星

### 1. 北极星问题

每次打开 Learning OS，应当在五秒内回答：

1. 我现在处于六个月计划的什么位置？
2. 本月和本周正在形成什么能力？
3. 今天最重要的任务是什么？
4. 今天为什么要学它？
5. 按什么步骤执行？
6. 需要形成什么成果？
7. 什么证据代表今天真正完成？

### 2. 北极星结果

Learning OS 的核心结果不是页面访问量、文件数量或知识节点数量，而是：

> **计划中的能力里程碑被可验证地完成。**

### 3. 核心产品指标

优先关注：

- 计划任务完成后形成成果的比例。
- 核心知识节点达到 L2、L3、L4 的比例。
- 已理解节点中拥有实践证据的比例。
- 每周计划与实际执行的偏差。
- 复盘产生有效计划调整的次数。
- 端到端项目里程碑的完成情况。

不把以下指标作为主要成功标准：

- 导入了多少文件。
- 收藏了多少资料。
- 页面连续使用多少天。
- 简单标记为“已完成”的节点数量。

## 五、产品与学习运行模型

> 注意：下面是 Learning OS 的产品运行模型，不是 AI Native 技术体系的“六层功能架构”。两者不能混为一谈。

Learning OS 由六个相互连接的子系统组成。

### 1. 目标系统

回答“为什么学”和“六个月后达到什么状态”。

主要内容：

- 六个月总体目标。
- 最终能力画像。
- 核心项目或作品目标。
- 成功标准。
- 不在本期范围内的内容。

输出：六个月目标和最终验收标准。

### 2. 计划系统

回答“按照什么顺序推进”。

主要内容：

- 六个月路线图。
- 月度目标和里程碑。
- 周计划。
- 每日任务。
- 优先级、依赖关系和时间安排。

输出：当前需要执行的任务队列。

### 3. 知识系统

回答“任务涉及哪些知识，以及它们如何关联”。

主要内容：

- AI Native 六层功能架构。
- 三条跨层运行流。
- 两类横向保障。
- 知识主题、知识节点和前置依赖。
- 资料、概念、模式、组件和机制。

输出：当前任务所需的知识上下文。

### 4. 学习执行系统

回答“今天具体怎么做”。

主要内容：

- 每日学习会话。
- 阅读和分析。
- 四问学习卡。
- 案例与反例。
- 练习、实验和真实任务。
- 与 AI 的讨论、质疑、评估和优化。

输出：学习行为和初步成果。

### 5. 成果与证据系统

回答“产生了什么，以及如何证明有效”。

主要内容：

- 学习总结。
- 知识卡。
- 案例拆解。
- 代码和实验。
- 项目交付物。
- 测试、Evals、指标和反馈。
- 决策记录和失败记录。

输出：可复查、可追踪、可关联的能力证据。

### 6. 复盘与调整系统

回答“结果说明了什么，接下来如何调整”。

主要内容：

- 日复盘。
- 周复盘。
- 月度验收。
- 知识与证据缺口。
- 计划偏差。
- 学习方法调整。
- 后续任务重排。

输出：状态更新、问题清单和修订后的计划。

### 7. 两个底座

六个子系统建立在两个底座上：

#### Markdown 与 Git 数据底座

- Markdown 是正式内容的唯一可信来源。
- Git 记录计划、知识和能力演进。
- 前端界面只是 Markdown 的任务化投影。
- 临时草稿可以保存在浏览器，但正式成果必须回到工程。

#### AI 协作底座

- AI 帮助解释、质疑、生成练习、评估输出和发现缺口。
- AI 不代替学习者完成最终判断。
- AI 给出的结论需要来源、实践或评估证据支持。
- 重要共识必须沉淀为工程内文档，不能只停留在对话中。

## 六、三条学习运行流

为了便于理解，Learning OS 也可以用三条运行流描述。

### 1. 控制流：计划如何驱动行动

```text
六个月目标
→ 月度里程碑
→ 周计划
→ 每日任务
→ 学习步骤
→ 完成条件
```

控制流决定下一步做什么，不由知识树自动决定。

### 2. 数据流：学习如何形成成果

```text
学习资源
→ 理解与讨论
→ 学习卡
→ 案例和练习
→ 项目输出
→ Markdown 成果
```

数据流描述输入如何逐渐变成可复用输出。

### 3. 反馈流：证据如何改变计划

```text
练习结果 / 测试 / Evals / 项目反馈
→ 判断能力状态
→ 发现知识或实践缺口
→ 日、周、月复盘
→ 调整后续计划
```

没有反馈流，计划只能按原定顺序机械执行，不能真正适应学习结果。

## 七、核心对象及其关系

### 1. 核心对象

| 对象 | 作用 | 典型文件 |
|---|---|---|
| Goal | 定义六个月最终结果 | 六个月总体规划 |
| Milestone | 定义月度或阶段能力目标 | 月度计划 |
| Guide | 定义学习规则和执行方法 | 完整执行指导手册 |
| WeeklyPlan | 选择本周重点与任务 | 周计划 |
| Task | 定义当天可以完成的行动 | 每日任务 |
| KnowledgeNode | 组织一个可学习的知识单元 | 知识地图、节点卡 |
| Resource | 提供外部输入 | 文章、课程、文档、代码库 |
| Session | 记录一次真实学习过程 | 每日学习记录 |
| Artifact | 保存学习形成的输出 | 总结、案例、代码、设计 |
| Evidence | 证明某项能力已经形成 | 测试、Evals、指标、反馈 |
| Review | 解释结果并调整计划 | 日、周、月复盘 |

### 2. 关系模型

```text
Goal
└── Milestone
    └── WeeklyPlan
        └── Task
            ├── follows → Guide
            ├── learns → KnowledgeNode
            ├── uses → Resource
            └── executed_as → Session
                               ├── produces → Artifact
                               └── produces → Evidence

Artifact / Evidence
├── proves → KnowledgeNode capability level
├── completes → Task
└── evaluated_by → Review

Review
└── adjusts → Milestone / WeeklyPlan / Task
```

### 3. 关键约束

- 一个任务可以关联多个知识节点。
- 一个知识节点可以被多个月度任务反复使用。
- 一个成果可以支持多个节点，但必须明确主要证明对象。
- “任务完成”和“节点掌握”是两个不同状态。
- 月度计划决定学习优先级，知识地图只描述知识关系。
- 时间线是对象变化的查看方式，不是独立的数据类型。

## 八、六个月、月、周、日如何贯通

### 1. 六个月层

六个月计划回答：

- 最终要具备哪些能力？
- 要完成什么端到端项目？
- 六个月分成哪些阶段？
- 最终如何验收？

### 2. 月度层

月度计划回答：

- 本月重点形成哪部分能力？
- 本月需要覆盖哪些知识主题？
- 本月需要完成哪些练习或项目里程碑？
- 本月的验收证据是什么？

`第1月_完整执行指导手册_V2.0` 属于本月执行规则的重要来源。Learning OS 应读取和呈现它的要求，而不是重新发明另一套学习流程。

### 3. 周层

周计划回答：

- 本周承接哪个月度目标？
- 本周要解决什么关键问题？
- 本周要学习哪些核心节点？
- 本周至少形成什么成果和证据？
- 哪些内容明确不做？

### 4. 每日层

每日任务回答：

- 今天最重要的学习结果是什么？
- 今天完成哪些明确动作？
- 使用哪些资料？
- 关联哪些知识节点？
- 形成什么 Markdown 成果？
- 怎样判断今天完成？
- 如果没有完成，下一步如何续接？

### 5. 贯通规则

任何每日任务都应该能沿路径追溯：

```text
每日任务
→ 本周重点
→ 本月里程碑
→ 六个月能力目标
```

如果一个任务无法追溯到上层目标，需要说明它为什么临时加入，否则不进入正式计划。

## 九、一次完整的每日学习闭环

每日学习不是简单地打开一个知识节点，而是执行一次完整学习会话。

### 阶段 1：定位

回答：

- 今天承接哪个月度和周目标？
- 为什么今天学习这个主题？
- 前一天停在什么位置？
- 今天的最小完成结果是什么？

### 阶段 2：输入

完成：

- 阅读计划指定的资料。
- 查看相关知识节点和前置内容。
- 记录问题、冲突和不理解之处。

### 阶段 3：理解

围绕知识节点回答四个问题：

1. 它是什么？
2. 解决什么问题？
3. 什么时候使用或不使用？
4. 怎样证明它有效？

### 阶段 4：实践

至少完成一种活动：

- 案例拆解。
- 反例分析。
- 小练习。
- 代码实验。
- 架构设计。
- 真实项目任务。

### 阶段 5：验证

使用明确标准检查：

- 是否能脱离资料解释？
- 是否能判断边界和权衡？
- 是否能在新情境中使用？
- 是否有可复查结果？
- AI 的评估是否有具体理由和证据？

### 阶段 6：沉淀

把结果保存为正式 Markdown 或项目文件，并关联：

- 对应每日任务。
- 对应知识节点。
- 对应月度里程碑。
- 对应验证证据。

### 阶段 7：收尾

记录：

- 今天完成了什么？
- 哪些问题仍未解决？
- 节点能力等级是否变化？
- 明天从哪里继续？
- 计划是否需要调整？

## 十、日、周、月复盘机制

### 1. 日复盘

目的：保证下一次可以无摩擦继续。

最小输出：

- 今日完成结果。
- 新增成果和证据。
- 未解决问题。
- 当前节点状态。
- 下一步动作。

### 2. 周复盘

目的：判断实际学习是否推进了本周能力目标。

检查：

- 计划任务完成情况。
- 成果与证据是否匹配。
- 哪些节点停留在 L1 或 L2。
- 哪些任务消耗很大但价值不高。
- 下周应继续、停止或调整什么。

输出：周复盘和修订后的下周计划。

### 3. 月度验收

目的：判断本月里程碑是否真正完成。

检查：

- 本月目标能力是否达到要求等级。
- 本月知识主题是否形成系统理解。
- 本月实践或项目里程碑是否完成。
- 是否存在可独立复查的证据。
- 是否能够综合讲解本月主题。
- 下月计划是否需要重新排序。

月度验收不是简单汇总每天学过的内容，而是一次能力评估。

## 十一、现有文档的系统位置

现阶段已有文档需要按“职责”而不是按“文件夹”理解。

| 已有内容 | 系统位置 | Learning OS 应如何使用 |
|---|---|---|
| 六个月学习规划 | 目标系统、计划系统 | 展示整体路线、月份和最终验收 |
| 第一个月计划 | 计划系统 | 生成本月里程碑、周重点和任务来源 |
| 第1月_完整执行指导手册_V2.0 | 计划系统、执行系统 | 约束每日流程、学习方法和完成标准 |
| AI Native 知识地图 | 知识系统 | 提供任务关联、知识定位和依赖关系 |
| 每日学习总结 | 成果系统 | 作为理解输出和学习时间线来源 |
| 案例、练习、代码 | 学习执行、成果系统 | 作为 L2、L3 能力证据 |
| 测试、Evals、项目反馈 | 证据系统 | 作为 L3、L4 能力证据 |
| 日、周、月复盘 | 复盘系统 | 更新状态并调整计划 |

后续需要对工程内现有文件进行一次正式盘点，为每份文档标记：

- 它属于哪个系统。
- 它是否仍然有效。
- 它与哪些目标、任务和节点关联。
- 它是计划、执行结果还是验证证据。

## 十二、AI 在 Learning OS 中的角色

AI 不是自动替学习者完成内容，而是承担六种协作角色。

### 1. 计划助手

- 把月度目标转化为周、日任务草案。
- 检查任务是否能够追溯到上层目标。
- 发现任务过载、依赖错误和优先级冲突。

### 2. 讲解者

- 根据当前水平解释概念。
- 提供对比、类比和反例。
- 指出理解中的模糊或错误之处。

### 3. 质疑者

- 追问使用条件和不使用条件。
- 要求说明权衡和失败场景。
- 防止只记结论、不理解边界。

### 4. 练习设计者

- 根据知识节点和能力等级生成练习。
- 控制练习难度和前置依赖。
- 把学习内容映射到真实场景。

### 5. 评估者

- 根据明确标准评估总结、方案、代码和证据。
- 指出具体缺口，不只给出笼统分数。
- 区分表达问题、知识问题和实践问题。

### 6. 复盘伙伴

- 汇总计划和实际执行偏差。
- 发现重复失败模式。
- 提出调整建议，但由学习者做最终决定。

### 7. 人与 AI 的责任边界

学习者负责：

- 选择最终目标和优先级。
- 对理解和决策承担责任。
- 完成关键练习与真实实践。
- 判断证据是否可信。
- 决定是否调整计划。

AI 负责提高理解、反馈和组织效率，但不能把“AI 生成了一份答案”视为学习者已经掌握。

## 十三、Markdown 与数据原则

### 1. 唯一可信来源

正式数据以工程中的 Markdown 和项目文件为准。

```text
Markdown / 项目文件 = 内容与证据
Git = 历史与演进
界面 = 读取、执行、关联和展示
浏览器本地存储 = 临时草稿与界面状态
```

### 2. 为什么现阶段不使用后端和数据库

- 当前是单人、本地优先的学习系统。
- 学习结构仍在演进。
- Markdown 更容易被人、AI 和 Git 同时使用。
- 当前主要问题是内容关系和运行闭环，不是数据规模。

未来出现多端同步、多人协作、后台自动任务、大规模语义检索或复杂查询时，再考虑本地服务、SQLite 或云端后端。

### 3. 最小元数据

正式学习文件建议逐步具备以下字段：

```yaml
---
id: unique-id
title: 文件标题
type: plan | task | node | session | artifact | evidence | review
status: draft | active | completed | verified | archived
created: YYYY-MM-DD
updated: YYYY-MM-DD
goal: 对应六个月目标
milestone: 对应月度里程碑
week: 对应周计划
tasks:
  - 关联任务 ID
nodes:
  - 关联知识节点 ID
evidence_for:
  - 被证明的能力或节点
sources:
  - 外部资料
---
```

字段应逐步采用，不要求一次性重写所有旧文档。优先为新增文件和关键计划文件添加。

## 十四、未来界面的信息架构约束

在本共识确认前不继续设计具体界面。未来界面必须遵守以下信息架构。

### 1. 今日执行工作台是默认入口

首页首先展示：

- 六个月、月、周、日位置。
- 今日最重要结果。
- 今日任务及完成条件。
- 当前学习步骤。
- 应形成的成果和证据。
- 上次中断位置。

### 2. 路线图负责展示计划

路线图展示：

- 六个月阶段。
- 月度目标。
- 当前周计划。
- 里程碑及验收状态。

路线图不是知识地图。

### 3. 知识地图是内容索引

知识地图用于：

- 理解 AI Native 知识结构。
- 定位当前任务涉及的节点。
- 查看前置、相关和后续知识。
- 检查节点能力等级和证据缺口。

知识地图不负责决定今天学什么。

### 4. 学习工作台围绕任务，而不只围绕节点

一次学习工作台需要同时展示：

- 今天的任务和上层目标。
- 相关知识节点。
- 执行指导手册要求。
- 学习资料。
- 当前学习步骤。
- 输出区域。
- 完成条件和证据要求。

节点学习卡是工作台中的一个步骤，不是完整学习流程。

### 5. 学习档案统一成果和证据

学习档案可以按多种方式查看同一批内容：

- 按时间。
- 按月份和周。
- 按知识节点。
- 按成果类型。
- 按能力等级。
- 按是否具有验证证据。

### 6. 复盘中心负责反馈

复盘中心展示：

- 计划与实际偏差。
- 能力状态变化。
- 缺少实践或证据的节点。
- 月度里程碑风险。
- 下一步调整建议。

## 十五、Learning OS 第一阶段范围

### 1. 第一阶段必须解决

- 能读取六个月、月、周、日计划。
- 能明确展示今天的任务和完成标准。
- 能把任务关联到知识节点。
- 能按照执行手册完成一次学习会话。
- 能形成并写回 Markdown 成果。
- 能把成果关联为能力证据。
- 能完成日复盘，并为下一天提供续接点。
- 能查看月度里程碑的真实进展。

### 2. 第一阶段暂不解决

- 多用户和团队协作。
- 云端账号体系。
- 复杂数据库。
- 社交、排行榜和游戏化积分。
- 自动替学习者生成全部成果。
- 大而全的课程平台。
- 为视觉效果而增加的复杂交互。

### 3. 第一阶段产品判断标准

界面只有满足以下条件才有价值：

> 它能让每日学习比直接打开 Markdown 更清楚、更连续、更容易完成，并且不会破坏 Markdown 作为唯一可信来源。

如果界面只是换一种方式浏览文件和知识节点，就没有达到 Learning OS 的目标。

## 十六、产品原则

1. **目标优先于内容**：先知道要形成什么能力，再选择学习内容。
2. **执行优先于展示**：首页服务今天的行动，不展示全部系统复杂度。
3. **证据优先于状态**：不能只手工勾选“已掌握”。
4. **任务连接知识**：计划任务和知识节点必须建立双向关联。
5. **知识连接实践**：核心节点必须经过案例、练习或真实任务。
6. **复盘必须改变后续行动**：没有调整结果的复盘只是总结。
7. **Markdown 保持可独立使用**：即使界面消失，学习成果仍然完整。
8. **AI 增强学习者，不代替学习者**：生成内容不等于掌握。
9. **逐步增加复杂性**：先建立可靠闭环，再考虑数据库、自动化和智能推荐。
10. **所有视图服务同一运行模型**：不为每个功能建立彼此孤立的数据体系。

## 十七、共识确认清单

在进入下一轮界面设计前，需要确认以下共识。

### A. 关于目标

- [ ] 核心目标是六个月系统掌握 AI Native，而不是建设知识管理网站。
- [ ] “掌握”采用 L0—L4 能力状态，而不是简单的已学/未学。
- [ ] 最终必须包含端到端项目和可复查证据。

### B. 关于运行方式

- [ ] 六个月目标逐层落到月、周、日。
- [ ] 每日任务必须能够追溯到月度和六个月目标。
- [ ] 每日学习采用定位、输入、理解、实践、验证、沉淀、收尾七阶段闭环。
- [ ] 周复盘和月度验收可以调整后续计划。

### C. 关于知识地图

- [ ] 知识地图负责组织内容，不决定每天的学习顺序。
- [ ] 月度计划决定当前知识优先级。
- [ ] 节点学习卡只是完整学习任务中的一个步骤。

### D. 关于成果和证据

- [ ] Markdown 文件数量不作为核心进度指标。
- [ ] 核心节点需要理解、边界、实践和验证证据。
- [ ] 成果必须关联任务、知识节点和里程碑。

### E. 关于技术与界面

- [ ] 现阶段 Markdown 与 Git 是正式数据底座。
- [ ] 暂时不建立后端和数据库。
- [ ] 默认入口是今日执行工作台。
- [ ] 界面应投影现有计划和手册，而不是另建一套规则。
- [ ] 本共识确认后再开始界面信息架构和视觉设计。
