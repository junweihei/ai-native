# AI Native D3 学习总结：Workflow、Agent 与任务路径设计

日期：2026-08-26  
学习资源：[Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)

## 一、今天解决的核心问题

今天学习的重点不是怎样开发一个 Agent，而是建立一种机制选择能力：

> 面对一个业务任务，应该使用单次 LLM、固定 Workflow，还是由模型动态决定任务路径的 Agent？

我形成的核心认识是：

> Agent 并不天然优于 Workflow。应从能够解决问题的最简单方案开始，通过评测确认简单方案的不足；只有增加复杂度能够可测量地改善结果时，才引入多步 Workflow 或 Agent。

复杂系统通常以更高的成本、延迟和错误风险，换取更强的任务处理能力与灵活性。

因此，正确的设计顺序应该是：

```text
明确业务目标
→ 尝试单次 LLM
→ 优化 Prompt、Context、示例和检索
→ 建立评测并识别失败
→ 判断是否需要 Workflow
→ 只有总体路径无法预先确定时才考虑 Agent
```

## 二、Agentic System 的两种形态

Anthropic 将使用 LLM 和工具完成任务的系统统称为 Agentic Systems，并在架构上区分为两种形态：

```text
Agentic Systems
├── Workflow：总体任务路径由代码预先定义
└── Agent：总体任务路径由模型根据环境反馈动态决定
```

两者都可以使用：

- LLM；
- Prompt 和 Instructions；
- RAG；
- Memory 或任务状态；
- Tools；
- API 或 MCP；
- Guardrails；
- 人工确认。

因此，不能根据“有没有使用 LLM”“有没有 RAG”或者“有没有调用工具”判断一个系统是不是 Agent。

真正的判断标准是：

> 下一步主要由预定义代码路径决定，还是由模型根据当前环境反馈动态决定？

### 1. Workflow

Workflow 是：

> LLM 和工具按照预先定义的代码路径进行编排的系统。

Workflow 的主要特点是：

- 总体任务步骤提前确定；
- 分支、顺序和循环结构由代码控制；
- 模型只负责流程中的特定任务；
- 更容易测试、追踪和审计；
- 运行结果通常更可预测、更一致；
- 出现错误时更容易定位具体环节。

Workflow 适合：

- 任务步骤比较稳定；
- 任务能够清晰拆分；
- 强调一致性和可控性；
- 不需要模型重新规划整个任务；
- 处理过程需要审计；
- 高风险动作必须按固定规则执行。

例如：

```text
接收报销单
→ 模型抽取金额和费用类型
→ 程序校验字段
→ 固定规则判断是否超标
→ 进入审批流程
```

虽然其中使用了 LLM，但任务路径仍由代码控制，所以它属于 Workflow。

### 2. Agent

Agent 是：

> LLM 根据任务目标和环境反馈，动态决定处理流程和工具使用方式，并保留对任务完成方式控制权的系统。

Agent 的主要特点是：

- 目标相对明确，但具体步骤无法完全预先确定；
- 模型需要根据中间结果判断下一步；
- 可以动态选择工具；
- 可以调整计划、增加步骤或改变搜索方向；
- 可能运行多个回合；
- 遇到阻碍时可以请求用户提供信息或判断；
- 需要停止条件、权限边界、日志和人工接管。

Agent 适合：

- 步骤数量无法预先确定；
- 必须根据工具结果改变计划；
- 每次任务需要处理的对象和子任务不同；
- 需要在多个工具之间动态选择；
- 任务具有一定开放性；
- 系统可以获得可验证的环境反馈；
- 错误后果和运行成本可以控制。

例如：

```text
用户要求修复一个代码问题
→ Agent 阅读项目
→ 判断可能涉及哪些文件
→ 搜索相关代码
→ 修改代码
→ 运行测试
→ 根据测试失败调整方案
→ 再次修改和测试
→ 测试通过后提交结果
```

需要修改哪些文件、修改几次以及使用哪些工具，都不能在开发时完全确定，因此更适合 Agent。

### 3. Workflow 与 Agent 的核心区别

```text
Workflow
目标
→ 程序规定步骤
→ LLM 完成指定子任务
→ 程序决定下一步
→ 输出结果
```

```text
Agent
目标
→ LLM 制定初步计划
→ 选择并调用工具
→ 环境返回真实结果
→ LLM 判断任务进展
→ 动态调整下一步
→ 完成、请求人工或停止
```

可以用一句话概括：

> Workflow 的总体道路由开发者提前修好，模型在道路中完成任务；Agent 只有目标和边界，具体道路可以由模型边走、边验证、边调整。

## 三、共同基础：增强型 LLM

Workflow 和 Agent 的基础构件是增强型 LLM。

```text
增强型 LLM
= Language Model
+ Retrieval
+ Tools
+ Memory 或任务状态
```

这些能力分别解决不同问题：

| 能力 | 主要作用 |
|---|---|
| Language Model | 理解、分类、抽取、生成和判断 |
| Retrieval | 获取模型参数之外的相关资料 |
| Tools | 查询外部系统或执行动作 |
| Memory/State | 保存当前任务需要的历史信息和运行状态 |

增强型 LLM 不等于 Agent。

如果模型只在固定流程中的某一步使用检索或工具，系统仍然可以是 Workflow。只有当模型开始动态控制任务路径和工具选择时，才更接近 Agent。

增强能力的设计重点不是“接入多少工具”，而是：

- 是否与具体任务真正相关；
- 工具名称和参数是否容易理解；
- 工具边界是否清楚；
- 工具返回值是否足以判断任务进展；
- 接口是否具有完整文档；
- 是否经过真实样例测试。

例如，一个固定知识问答流程可以使用：

```text
用户提问
→ 固定执行知识检索
→ 把检索结果放入 Context
→ LLM 生成回答
→ 固定格式输出
```

这个系统包含 Retrieval 和 LLM，但路径仍然固定，因此属于增强型 LLM Workflow，而不是 Agent。

## 四、五种 Workflow 的高层模型

五种 Workflow 不应孤立记忆，可以从“任务路径怎样组织”来理解。

| 模式 | 高层特点 | 总体路径由谁决定 |
|---|---|---|
| Prompt Chaining | 固定串行 | 代码预先规定步骤 |
| Routing | 固定分流 | 代码规定分支结构 |
| Parallelization | 固定并行 | 代码规定并行任务和汇总方式 |
| Orchestrator-Workers | 动态拆解 | 整体结构固定，模型动态产生子任务 |
| Evaluator-Optimizer | 循环优化 | 整体循环固定，模型动态评价和修改 |

可以简化记忆为：

```text
固定串行
→ Prompt Chaining

固定分流
→ Routing

固定并行
→ Parallelization

总体结构固定，子任务动态拆解
→ Orchestrator-Workers

总体循环固定，根据反馈反复改进
→ Evaluator-Optimizer
```

五种 Workflow 的共同点是：

> 系统的总体控制结构仍由开发者预先规定，模型只在结构允许的范围内完成生成、分类、拆解、评价或优化。

它们的本质差异在于：

> 任务路径采用串行、分流、并行、动态拆解，还是反馈循环。

五种 Workflow 与 Agent 的完整关系是：

```text
Agentic Systems
│
├── Workflow：总体路径由代码控制
│   ├── 固定串行 → Prompt Chaining
│   ├── 固定分流 → Routing
│   ├── 固定并行 → Parallelization
│   ├── 动态拆解 → Orchestrator-Workers
│   └── 循环优化 → Evaluator-Optimizer
│
└── Agent：总体任务路径由模型根据环境反馈动态控制
```

Agent 不应作为“第六种 Workflow”与前五种模式直接并列。

## 五、五种常见 Workflow 模式

### 1. Prompt Chaining：固定串行

Prompt Chaining 将任务拆成固定的连续步骤，每次 LLM 调用处理上一步的输出。

```text
输入
→ LLM 任务一
→ 中间检查 Gate
→ LLM 任务二
→ 最终结果
```

适用条件：

- 任务能够清晰拆成固定子任务；
- 子任务之间有明确顺序；
- 每一步都比完整任务更简单；
- 中间结果可以检查；
- 可以接受用更高延迟换取更高准确性。

示例：

```text
生成文章提纲
→ 检查提纲是否符合标准
→ 根据提纲撰写正文
→ 检查正文格式
```

Prompt Chaining 中可以加入程序化 Gate：

```text
中间结果符合标准
├── 是 → 继续下一步
└── 否 → 返回修改或停止
```

Prompt Chaining 的价值不是单纯增加调用次数，而是：

> 把一个复杂任务拆成多个更简单、更容易检查的步骤，以更高延迟换取更高准确性和可控性。

### 2. Routing：固定分流

Routing 对输入进行分类，再把它发送到专门的流程、Prompt、工具或模型。

```text
用户输入
→ 分类
├── 普通咨询 → 知识问答流程
├── 退款申请 → 退款审核流程
└── 技术故障 → 技术支持流程
```

适用条件：

- 输入存在明确类别；
- 不同类别需要不同处理方式；
- 分类能够达到可接受的准确度；
- 专门流程比一个通用 Prompt 更可靠。

分类不一定必须由 LLM 完成，也可以使用：

- 固定规则；
- 传统分类算法；
- 小模型；
- LLM；
- 多种机制组合。

Routing 还可以把简单任务交给成本更低的模型，把复杂任务交给能力更强的模型，以平衡质量、速度和成本。

Routing 的价值是：

> 把不同性质的任务交给最适合它的处理机制，而不是要求一个通用 Prompt 同时处理所有输入。

### 3. Parallelization：固定并行

Parallelization 让多个相互独立的 LLM 调用同时运行，再以程序方式汇总结果。

它包括两种主要形式。

#### 3.1 Sectioning：任务分段

把任务拆成多个可以独立完成的子任务，并行执行。

```text
需求文档
├── 检查完整性
├── 检查一致性
├── 检查可测试性
└── 检查安全与权限
        ↓
     汇总结果
```

适用于：

- 子任务之间不相互依赖；
- 希望缩短处理时间；
- 每个检查维度需要独立注意力；
- 最终结果可以统一汇总。

Sectioning 的价值是：

> 让每个模型调用只关注一个明确维度，减少一次调用同时处理过多目标造成的遗漏。

#### 3.2 Voting：多次尝试或多视角判断

让多个调用处理同一问题，再综合不同结果。

适用于：

- 单次结果不够稳定；
- 需要多个分析视角；
- 希望降低遗漏风险；
- 可以定义汇总规则或判断阈值。

Voting 不一定是简单多数投票，还可以是：

- 不同角色分别审查；
- 不同 Prompt 检查不同风险；
- 多次独立判断后综合证据；
- 根据风险等级设置不同阈值。

Voting 的价值是：

> 通过多次独立判断或多视角分析提高结果置信度，而不是把某一次模型输出直接视为最终答案。

### 4. Orchestrator-Workers：动态拆解

Orchestrator-Workers 由中央 Orchestrator LLM 根据当前任务动态拆解子任务，交给 Worker LLM 执行，再汇总结果。

```text
复杂任务
→ Orchestrator 分析任务
→ 动态产生子任务
├── Worker 1
├── Worker 2
└── Worker 3
→ Orchestrator 汇总
→ 最终结果
```

适用条件：

- 每次任务需要的子任务不同；
- 无法预先确定具体处理对象；
- 子任务能够分别执行；
- 最终结果需要统一整合。

它与 Parallelization 的区别是：

```text
Parallelization
子任务在开发时已经确定
```

```text
Orchestrator-Workers
子任务由 Orchestrator 根据当前输入动态产生
```

例如，审查不同项目的代码时，需要分析哪些文件、安排哪些子任务，通常取决于当前项目和任务，无法在开发时完全写死。

需要注意：

> Orchestrator-Workers 中的子任务虽然是动态的，但“编排器拆解—工作者执行—编排器汇总”的总体结构仍由开发者预先定义，因此 Anthropic 将其归入 Workflow。

### 5. Evaluator-Optimizer：循环优化

Evaluator-Optimizer 由一个 LLM 生成结果，另一个 LLM 根据明确标准进行评价并提出反馈，生成模型再根据反馈修改。

```text
Generator 生成
→ Evaluator 评价
→ 是否达到标准？
├── 是 → 输出
└── 否 → 提出反馈
          ↓
       Generator 修改
          ↓
       再次评价
```

适用条件：

- 评价标准能够明确表达；
- 人类反馈能够明显改善结果；
- Evaluator 可以产生类似的有效反馈；
- 多轮修改能带来可测量的价值；
- 可以设置质量阈值和最大迭代次数。

适用示例：

- 文学翻译；
- 高质量专业写作；
- 复杂研究和搜索任务；
- 可以根据明确标准逐轮改进的内容。

Evaluator-Optimizer 不适合：

- 评价标准模糊；
- 评价意见不能指导具体修改；
- 每轮优化收益很小；
- 无法定义停止条件。

需要注意：

> 评价内容和修改结果是动态的，但“生成—评价—修改”的循环结构及停止条件仍应由系统控制。

## 六、Agent：动态路径与受控运行循环

Agent 不是“给模型一个目标，然后让它无限运行”。

一个可控 Agent 应形成以下闭环：

```text
用户给出目标
        ↓
Agent 理解任务并制定计划
        ↓
选择并调用工具
        ↓
环境返回真实结果
        ↓
判断任务是否取得进展
        ↓
调整计划或选择下一步
        ↓
判断是否需要人工参与
        ↓
判断是否达到完成或停止条件
        ↓
完成任务 / 转交人工 / 安全停止
```

### 1. 环境反馈

Agent 必须从外部环境获得可观察结果，例如：

- 工具调用结果；
- 数据库查询结果；
- 文件内容；
- API 返回值；
- 代码编译结果；
- 自动化测试结果。

这些结果是判断任务进展的 Ground Truth。

Agent 不能只根据自己生成的文字判断任务是否已经完成，而要通过环境证据验证：

```text
我认为已经完成
≠ 任务真的完成

环境返回验证结果
→ 才能证明是否完成
```

### 2. 人工检查点

以下情况应暂停并让人参与：

- 缺少关键信息；
- 存在重要业务选择；
- 涉及高风险或不可逆操作；
- 超出当前权限；
- 连续尝试仍然失败；
- 结果需要专业判断；
- 用户必须确认后才能继续。

Human in the Loop 不是系统失败后的补救措施，而是 Agent 架构中的主动控制机制。

### 3. 停止条件

Agent 必须具有明确的停止条件，例如：

- 任务已完成；
- 达到最大迭代次数；
- 超出时间或成本预算；
- 连续多次没有取得进展；
- 遇到权限或安全限制；
- 必须转交人工。

如果没有停止条件，Agent 可能：

- 无限制调用模型和工具；
- 重复执行无效步骤；
- 累积错误；
- 超出预算；
- 执行不必要或高风险操作。

### 4. 错误恢复

Agent 应能够根据错误调整计划：

```text
工具调用失败
→ 分析失败原因
→ 修正参数或选择其他工具
→ 再次尝试
→ 达到重试上限
→ 停止或转人工
```

错误恢复不等于无限重试。它必须受到以下条件约束：

- 重试次数；
- 权限边界；
- 成本预算；
- 时间限制；
- 风险等级；
- 人工接管规则。

因此，Agent 的核心不是无限自主，而是：

> 在工具调用、环境反馈、进度判断、计划调整、人工检查和停止条件组成的受控循环中自主完成任务。

## 七、复杂度升级与机制选择方法

### 1. 复杂度升级路径

```text
单次 LLM
    ↓ 经过评测仍不满足要求
增强型 LLM
Prompt + Retrieval + Tools + Context
    ↓ 需要多个固定步骤
Workflow
    ├── 固定串行
    ├── 固定分流
    ├── 固定并行
    ├── 动态拆解
    └── 循环优化
    ↓ 连总体任务路径都无法提前确定
Agent
```

这不是必须逐级升级的技术路线，而是一个复杂度控制原则：

> 每增加一层复杂度，都必须说明它解决了什么已经被验证的问题。

### 2. 机制选择判断流程

面对一个任务时，我可以依次判断：

```text
只需要一次分类、抽取、总结或生成吗？
├── 是 → 单次 LLM
└── 否
     ↓
步骤是否必须按照固定顺序执行？
├── 是 → Prompt Chaining
└── 否
     ↓
输入是否存在明确类别并进入不同流程？
├── 是 → Routing
└── 否
     ↓
是否存在可同时执行的独立子任务或多视角检查？
├── 是 → Parallelization
└── 否
     ↓
总体协作结构已知，但具体子任务无法提前确定？
├── 是 → Orchestrator-Workers
└── 否
     ↓
结果是否可以根据明确标准反复评价和改进？
├── 是 → Evaluator-Optimizer
└── 否
     ↓
总体路径、步骤数量和工具选择是否都无法提前确定，
必须根据环境反馈持续调整？
├── 是 → 考虑 Agent
└── 否 → 重新检查是否可以使用更简单方案
```

这个判断流程不是严格排他的决策树。一个真实任务可能同时满足多个条件，需要组合不同模式。

### 3. 多种模式的组合

现实任务可以组合多种模式，例如：

```text
Routing 判断任务类型
→ Orchestrator 动态拆解子任务
→ Workers 并行执行
→ Evaluator 检查结果
→ 固定规则决定是否输出
```

也可以形成：

```text
用户输入
→ Routing 分类
→ Prompt Chaining 完成固定步骤
→ Parallelization 进行多维审查
→ Evaluator-Optimizer 修改结果
→ 人工确认后执行
```

组合模式时仍要保持：

- 总体结构清楚；
- 每个组件职责明确；
- 中间结果可以观察；
- 失败位置可以定位；
- 复杂度能够通过评测证明有价值。

## 八、三个核心设计原则

### 1. 保持简洁

- 从简单 Prompt 和单次调用开始；
- 先优化 Prompt、Context、示例和检索；
- 不为了使用 Agent 而设计 Agent；
- 只有评测证明必要时才增加复杂度；
- 上线前减少不必要的抽象层；
- 使用框架时仍要理解底层 Prompt、响应和工具调用。

框架能够简化开发，但也可能：

- 增加抽象层；
- 隐藏底层 Prompt 和模型响应；
- 增加调试难度；
- 诱导开发者过早使用复杂结构。

因此，应优先理解基本构件，再决定是否采用框架。

### 2. 保持透明

系统应让用户和开发者看见：

- 当前任务状态；
- 正在执行的主要步骤；
- 调用了什么工具；
- 获得了什么可观察结果；
- 为什么暂停或转交人工；
- 最终完成了什么。

透明主要指可观察的计划、动作、状态和证据，不等于必须暴露模型内部的隐藏推理过程。

### 3. 打磨 ACI

ACI 是 Agent-Computer Interface，即智能体与工具、API 或计算机之间的接口。

好的 ACI 应让模型：

- 容易选择正确工具；
- 容易理解参数；
- 不容易填错；
- 能识别工具边界；
- 能理解错误原因；
- 能在失败后修正操作。

可以类比为：

```text
HCI：让人容易使用计算机
ACI：让 Agent 容易、正确、安全地使用计算机和工具
```

## 九、工具的提示词工程

工具定义需要像主 Prompt 一样认真设计。

好工具应包含：

- 清晰、具体的名称；
- 准确的功能描述；
- 明确的参数含义；
- 输入格式和限制；
- 使用示例；
- 边界情况；
- 与相似工具的区别；
- 可以支持错误恢复的返回信息。

工具格式应遵循：

- 尽量接近模型熟悉的自然文本格式；
- 避免复杂转义和不必要的格式负担；
- 不要求模型维护容易出错的人工计数；
- 在工具调用前允许模型完成必要判断；
- 使用防呆设计降低出错概率。

例如，Agent 在改变当前目录后可能错误使用相对路径，因此可以把工具设计为必须提供绝对路径。

工具需要通过实际测试不断改进：

```text
设计工具
→ 使用多种输入测试
→ 记录模型常犯错误
→ 修改名称、参数或描述
→ 再次测试
```

设计工具时，我需要站在模型角度检查：

- 模型能否仅根据名称理解工具用途？
- 参数之间是否容易混淆？
- 是否存在两个功能高度相似的工具？
- 错误信息能否帮助模型修正？
- 能否通过参数约束阻止危险操作？
- 是否提供了足够的示例和边界说明？

设计 Agent 时，工具接口质量可能比增加更复杂的 Prompt 更重要。

## 十、应用场景与迁移检查清单

### 1. 客户服务

客户服务是当前较有前景的 Agent 应用场景，因为：

- 任务天然以对话方式进行；
- 需要查询客户、订单和知识库信息；
- 可能需要退款、更新工单等系统动作；
- 任务完成结果能够定义；
- 高风险动作可以加入人工确认。

一个客户服务 Agent 可以形成：

```text
用户提出问题
→ Agent 判断用户意图
→ 查询客户和订单信息
→ 检索知识库
→ 判断是否需要执行动作
→ 高风险动作请求人工确认
→ 返回结果并记录处理过程
```

### 2. 编程 Agent

编程任务适合 Agent 的原因包括：

- 可以通过编译和测试获得环境反馈；
- Agent 可以根据测试失败持续修改；
- 代码环境和任务边界相对明确；
- 结果可以通过自动化测试验证。

一个编程 Agent 可以形成：

```text
读取任务
→ 分析项目
→ 定位相关文件
→ 修改代码
→ 运行测试
→ 根据测试结果继续调整
→ 测试通过
→ 人工审查
```

自动化测试不能完全替代人工审查。人工仍需判断代码是否符合：

- 业务目标；
- 整体架构；
- 安全要求；
- 代码规范；
- 长期维护需要。

客户服务和编程不是所有 Agent 的必然成功场景，而是当前较有前景、较容易建立反馈闭环的领域。

### 3. 我的迁移检查清单

以后遇到一个 AI 任务时，我会依次问：

1. 单次 LLM 加 Prompt、RAG 或示例是否已经足够？
2. 如果不够，具体失败证据是什么？
3. 任务步骤能否提前确定？
4. 应该采用串行、分流、并行、动态拆解还是循环优化？
5. 子任务是预先固定的，还是必须根据输入动态产生？
6. 是否存在明确、可执行的评价标准？
7. 是否必须根据环境反馈动态改变下一步？
8. 系统可以从哪里获得 Ground Truth？
9. 哪些步骤必须人工确认？
10. 任务完成、失败和停止条件是什么？
11. Agent 增加的成本、延迟和风险是否值得？
12. 怎样通过评测证明复杂方案确实更好？

## 十一、核心结论与资料时间边界

### 1. 今天最重要的结论

> Workflow 和 Agent 都可以使用 LLM、RAG、Tools、API 和 MCP。真正的区别在于总体任务路径由预定义代码控制，还是由模型根据环境反馈动态控制。

> 五种 Workflow 的本质差异，是任务路径采用固定串行、固定分流、固定并行、动态拆解还是反馈循环。

> Orchestrator-Workers 和 Evaluator-Optimizer 虽然包含模型的动态判断，但总体控制结构仍是预定义的，因此仍属于 Workflow。

> Agent 不应作为第六种 Workflow。Agent 是与 Workflow 并列的另一种 Agentic System，其总体任务路径可以由模型动态决定。

> 一个可靠 Agent 的关键不是自主性有多强，而是能否在环境反馈、权限边界、人工检查、停止条件和日志审计的约束下完成任务。

> 构建 Agentic System 的目标不是得到最复杂的系统，而是得到最适合当前任务、能够通过评测证明有效的系统。

### 2. 资料的时间边界

本文发布于 2024 年 12 月。Anthropic 当前页面已经提示，相关工具生态此后发生了变化。

因此：

- Workflow、Agent 和五种模式仍可作为重要架构认知；
- “简单优先、评测驱动、工具接口优先”的原则仍然有效；
- 具体框架、SDK 和产品选型需要核对当前官方资料；
- 不能把文章中的具体工具状态直接视为当前最新技术选型结论。
