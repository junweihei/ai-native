## 1. 使用方式

本手册把网站建设拆成 16 个顺序步骤。每一步都应作为一个独立任务执行，使用独立分支和 Worktree；前一步通过门禁并形成可审查提交后，再开始依赖它的下一步。不要把全部提示词一次性投入同一个任务。

执行约束：

1. 每次先阅读仓库根目录 `AGENTS.md` 和三份 V1.0 基线文档。
2. GitHub 是唯一交接中心；一个任务对应一个分支和一个 Worktree。
3. 使用 `feature/`、`fix/`、`refactor/`、`test/`、`docs/` 或 `cloud/` 前缀，不直接合并 `main`。
4. 保留用户已有改动，不修改无关文件，不提交生成依赖目录、密钥或本地状态。
5. 任何内容契约变化必须同步更新配置、索引、模板、测试和文档。
6. 每步结束都检查差异、运行仓库检查和相关测试，并报告文件、结果与风险。
7. 规格、设计、数据契约或验收标准之间发生冲突时先停止实现，记录决策，不自行选择一个版本继续。

## 4. 分步执行说明与提示词

### 步骤 01：基线审计与需求追踪表

**目标：** 把产品规格、设计系统、验收标准和现有内容运行模型转换成一份无冲突的执行追踪表。

**主要产出：**

- 页面 × 用户流程 × FR × AC 追踪矩阵。
- P0/P1/P2 交付清单。
- 冲突、缺口、待决问题和决策记录。
- 三份文档共识门禁 DG-01—DG-10 的逐项结论。

**完成门禁：** 所有 FR 都有页面和验收场景；所有 P0 验收都能追溯到需求；无未记录的产品冲突。本步骤不写网站代码、不选择技术栈。

**提示词：**

```text
完成 AI Native Learning OS 网站建设的基线审计。阅读三份 V1.0 基线、Learning OS 产品与学习运行模型、学习执行规则、内容目录契约、配置文件和 web/README.md。建立一份可执行的需求追踪文档，至少包含：页面/流程、PS、FR、AC、优先级、依赖、所需数据、设计状态、实现状态、验收状态。逐项评审 DG-01—DG-10，列出冲突、缺口、歧义、影响和建议决策；不要自行改变已经确认的产品原则。把“今日 → 任务工作台 → 成果/证据 → 日复盘 → 续接点”标为发布阻断主路径。只产出规划和追踪文档，不编写网站代码，不选择技术栈。完成后运行仓库检查并给出能否进入信息架构设计的明确结论。
```

### 步骤 02：信息架构、页面模型与核心任务流

**目标：** 把规格转换成页面结构、导航规则和端到端流程。

**主要产出：**

- 五个一级入口和两个上下文页面的页面模型。
- UF-01—03 与 AC-P0-01—12 的逐屏流程。
- 页面进入/退出、返回上下文、深链接、空/错/阻塞路径。
- 桌面和窄屏的信息优先级说明。

**完成门禁：** 用户不经过知识地图即可在一次主操作内进入今日任务；路线图与知识地图职责无混淆；每个 P0 场景都有恢复路径。

**提示词：**

```text
基于已通过的需求追踪表，为 AI Native Learning OS V1 设计完整信息架构和核心任务流。定义“今日、路线图、知识地图、学习档案、复盘”五个一级入口，以及“任务工作台、知识节点详情”两个上下文页面。为每个页面写清用户问题、进入条件、主要信息、唯一主行动、次要行动、退出去向、返回上下文和所覆盖的 PS/FR/AC。逐屏描述 UF-01、UF-02、UF-03，并补充空状态、部分数据、过期、错误、只读、阻塞和未保存内容路径。分别说明桌面、中宽和窄屏的信息排序。不制作高保真视觉，不写代码，不做技术选型。输出可供线框设计直接使用的页面与流程文档，并检查 AC-P0-01—12 是否全部有落点。
```

### 步骤 03：低保真线框与完整状态设计

**目标：** 用低成本设计验证信息层级、主行动和异常恢复。

**主要产出：**

- 七个页面的桌面、窄屏关键线框。
- P0 主路径串联原型。
- 核心组件的加载、空、部分数据、错误、成功、只读、过期、阻塞状态。
- 键盘顺序、焦点移动和未保存保护说明。

**完成门禁：** 不依赖视觉润色也能完成 AC-P0 全流程；每页只有一个高强调主行动；错误与写回失败不会丢失输入。

**提示词：**

```text
根据产品基线、信息架构和任务流，制作 AI Native Learning OS 的低保真线框与状态规格。覆盖今日、路线图、知识地图、学习档案、复盘、任务工作台和知识节点详情；优先完整串联 P0 闭环。每个页面至少提供桌面和 320px 等效窄屏布局，标注内容优先级、主行动、次要行动、折叠/滚动行为、键盘焦点顺序和返回上下文。为按钮、任务卡、完成标准、证据卡、输入区、状态标签、反馈和对话框设计适用的加载、空、部分数据、错误、成功、禁用、只读、过期、阻塞状态。使用真实仓库对象作为示例，但不要修改学习结论或泄露受控材料。不要写生产代码或选择技术栈。完成后用 AC-P0-01—12 和 UI-01—09 做逐项自检，记录仍需产品决策的问题。
```

### 步骤 04：高保真视觉原型与设计门禁

**目标：** 将设计系统落到可评审的视觉和交互原型，冻结开发输入。

**主要产出：**

- 高保真桌面、窄屏 P0 原型。
- 七个页面的关键状态设计。
- 设计令牌、组件、内容文案和可访问性标注。
- 设计验收报告和开发标注。

**完成门禁：** DG-08、UI-01—10、AX 基线在设计层通过；冻结 V3 原型未反向覆盖新规格；P0 原型可从开始走到续接。

**提示词：**

```text
基于已通过的线框，完成 AI Native Learning OS V1 高保真视觉与交互原型。严格使用 website-design-system-v1.0.md 的“深色系统工作台 + 浅色学习纸张”方向、语义色、排版、间距、组件和内容规则。完整设计 P0 闭环的桌面与窄屏状态，并补齐七个页面的默认、加载、空、部分数据、错误、成功、只读、过期和阻塞关键画面。每个页面保持一个主行动；运行状态与 L0—L4 能力等级不可混淆；受控材料、写回失败、未保存保护和数据来源必须可见。V3 冻结原型只能作为视觉参考。产出可供开发实现的尺寸、令牌、组件状态、交互说明和文案，不写生产网站代码，不做技术选型。最后按 DG-08、UI-01—10、AX-01—06 生成设计验收报告，明确通过项、修订项和是否可进入数据契约设计。
```

### 步骤 05：网站数据契约 V1.0

**目标：** 定义网站需要的数据形状、关系、缺失行为和写回边界，不选择具体框架。

**主要产出：**

- 目标、里程碑、任务、节点、资源、成果、证据、复盘、会话的字段契约。
- 权威 Markdown → 生成索引 → 网站的映射。
- 状态枚举、L0—L4、关系完整性和索引版本规则。
- 读、草稿、预览差异、确认写回、冲突和失败协议。
- 真实样例和契约测试计划。

**完成门禁：** FR-01—14 都有数据支持；DT-01—05 可被验证；受控材料不可能通过普通索引预览泄露。

**提示词：**

```text
为 AI Native Learning OS 网站设计与技术无关的数据契约 V1.0。先审计 config/learning-content.json、模板注册表、内容 frontmatter、现有索引工具和第一个月运行映射，不改变 Markdown 的权威地位。定义 Goal/Milestone、Task、Knowledge Node、Resource、Artifact、Evidence、Review、Session 的最小字段、类型、必填/可选、关系、来源、缺失行为和示例；明确运行状态与 L0—L4 的分离。定义索引 schema_version、generated_at、来源提交/版本、关系完整性、未知状态、过期判断和向后兼容策略。单独定义受控材料的索引隔离规则，以及草稿、差异预览、用户确认、允许路径、冲突检测、原子写回、失败恢复的行为契约，但不决定实现技术。同步给出 FR/AC/DT 追踪表和契约测试清单。若内容契约需要变化，只提出变更方案和影响清单，本步骤不要直接批量迁移内容。完成后运行仓库检查。
```

### 步骤 06：技术选型与架构决策

**目标：** 在产品、设计和数据契约稳定后，选择最小可行技术方案。

**主要产出：**

- 候选方案比较与决策记录。
- 前端、内容读取/写回、本地运行、测试、构建和发布架构。
- 风险、迁移成本、退出策略和性能预算。
- AGENTS、setup/check、环境变量和文档更新计划。

**完成门禁：** 选择有证据、满足 P0 和数据主权约束；不因流行度引入无关运行时、数据库或服务。

**提示词：**

```text
现在产品、设计和数据契约已稳定，请为 AI Native Learning OS V1 完成技术选型与架构决策，但先不要搭建工程。以单用户、本地优先、Markdown 权威、生成索引读取、安全写回、可恢复草稿、响应式、WCAG 2.2 AA、可重复测试和未来可维护为硬约束。提出 2—3 个真正可行的最小方案，对比开发复杂度、写回能力、浏览器限制、本地/部署模型、测试能力、依赖规模、性能、跨平台、长期维护和退出成本。明确推荐方案及不选其他方案的原因；不得默认引入数据库、账号、云服务或模型供应商。定义逻辑架构、数据流、信任边界、错误恢复、测试分层、性能预算和支持矩阵，并列出落地时必须同步修改的 AGENTS.md、setup/check 脚本、依赖文件、环境变量示例和文档。把未验证假设转成小型技术验证任务。产出 ADR 和实施计划，评审通过前不写生产代码。
```

### 步骤 07：工程骨架与质量基线

**目标：** 按批准的 ADR 建立可复现、可测试、没有业务功能的工程骨架。

**主要产出：**

- 最小应用壳、构建与本地运行入口。
- 单元、组件、端到端和可访问性测试入口。
- 错误边界、日志、格式与静态检查基线。
- 更新后的 setup/check、AGENTS 和开发文档。

**完成门禁：** 新克隆/Worktree 可按文档初始化、运行、测试和构建；尚未硬编码学习路径或第二套状态。

**提示词：**

```text
依据已批准的技术 ADR，为 AI Native Learning OS 建立最小工程骨架。只实现应用壳、路由/页面占位、设计令牌入口、数据访问接口边界、错误边界和测试基础，不实现具体业务页面，不硬编码 content 路径或学习状态。更新 AGENTS.md、Windows 与 macOS/Linux setup/check 命令、依赖清单、环境变量示例、开发说明和忽略规则；确保没有密钥、构建产物或依赖目录进入版本控制。配置单元、组件、端到端、可访问性与静态检查的最小可运行样例。使用一个可替换的测试数据适配层证明工程边界，但不要建立平行权威数据。验证 fresh clone/Worktree 的初始化、开发启动、测试、构建和仓库检查，记录精确命令与结果。若依赖或锁文件变化，只做本步骤需要的最小改动。
```

```text
实现 AI Native Learning OS 的“今日工作台”，严格覆盖 PS-01、FR-01—03、FR-06、AC-P0-01—03 和 AC-P0-11。默认进入今日页，从数据契约和真实生成索引确定唯一可执行主任务；首屏呈现月/周/日位置、主任务、预计时间、上层能力目标和开始/继续主操作，并提供完成条件、主要成果、证据、门禁、上次中断点和下一动作。不得使用知识总量、文件数或打卡数据抢占主视觉。实现加载、无当前任务、多个候选任务、关系缺失、索引过期、只读和错误状态，不补造默认值。桌面、中宽、320px 窄屏和键盘操作均可用。添加对应单元、组件和端到端测试，使用可重复的 M01-D01/D02/D04 样例；运行全部相关检查并按 AC 编号报告结果。
```

### 步骤 09：任务工作台与受控学习流程

**目标：** 实现按学习协议执行任务的核心工作区。

**覆盖：** PS-03；FR-03—05、07；AC-P0-03—05、08、12。

**完成门禁：** 一次学习会话可以按协议推进；受控材料无普通路径泄露；首次版本不可静默覆盖。

**提示词：**

```text
实现任务工作台和受控学习流程，覆盖 PS-03、FR-03—05、FR-07、AC-P0-03—05、AC-P0-08、AC-P0-12。工作台同时显示任务目标和追溯、时间盒、依赖、步骤、门禁、允许资源、相关节点、主要/支持成果、模板、完成规则、自检和证据要求。按“定位→闭卷首做→指定输入→主动加工→成果→自检→只修一个问题→收尾”驱动状态；仅隐藏明确不适用的步骤。实现可恢复草稿、保存时间、离开保护、首次版本保留、开放条件满足后才显示受控材料、参考后修订差异和阻塞记录。搜索、摘要、关联卡、直接地址和客户端数据中都不能提前泄露受控内容。运行状态与能力等级分开。完成桌面/窄屏、键盘和异常状态，并添加针对受控材料绕过、刷新恢复、步骤错误和阻塞的自动化测试。
```

### 步骤 10：成果、证据与安全写回

**目标：** 打通从草稿到权威 Markdown 的受控提交链路。

**覆盖：** FR-05—07；AC-P0-06—08；DT-01—05。

**完成门禁：** 成功写回可追踪，失败不丢输入、不提前变更状态、不写出允许目录；冲突有明确恢复路径。

**提示词：**


## 5. 建议的任务与分支拆分

| 步骤 | 建议分支 | 冲突提示 |
|---|---|---|
| 01—04 | `docs/website-*` | 主要修改 `docs/product/` 与设计产物，避免并发改三份基线 |
| 05 | `feature/website-data-contract` | 可能涉及配置、索引和测试，单独排他执行 |
| 06 | `docs/website-architecture` | ADR 评审通过前不改依赖文件 |
| 07 | `feature/website-bootstrap` | 会改 AGENTS、脚本和锁文件，避免并行 |
| 08—14 | `feature/website-<capability>` | 每个能力一个分支；共用路由/Schema 变更需串行 |
| 15 | `test/website-v1-acceptance` | 缺陷修复按问题另开 `fix/` 分支更易审查 |
| 16 | `docs/website-v1-release` | 只做发布准备和文档，不混入新功能 |

## 6. 每一步的标准交付格式

每个任务结束时按以下格式交付：

```text
步骤与结论：完成 / 未完成 / 被阻塞
覆盖需求：PS / FR / AC 编号
变更文件：
关键决策：
检查与测试：命令、结果
验收证据：
未覆盖风险：
下一步门禁：通过 / 不通过
分支或 PR：
```

若门禁不通过，下一任务不是继续主路径，而是只修复当前门禁失败项。不得用新增功能掩盖核心闭环缺失。
